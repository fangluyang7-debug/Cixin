# 鸿蒙手机验证操作手册与结果回传

适用版本：包含本文件的 `harmony/mobile-scheduler` 分支。验证前记录 `git rev-parse HEAD`，不要混用旧初赛目录或此芯工程。

目的：确认代码在真实手机上运行正确，采集可复现对照数据。本文件不是已通过的手机测试报告。开发侧构建与主机测试结果见文档 03 的阶段五记录。

## 1. 本次需要验证的作品

应用级 AI 任务调度 HAR，以及使用它的鸿蒙原生 App。真实负载是 CPU 文本 Embedding、向量检索和分块缓存重建。

- 不需要此芯板、GPU 服务器或端侧生成式大模型。
- 不修改系统内核，不控制 CPU 频率，不调度其他 App。
- GPU/NPU 注入按钮只测试策略分支，不能证明相应硬件推理。
- 镜头、框选是交互示意，尚未接入图像识别。
- 功耗和续航显示“未测量”；本轮不能得出具体节电百分比。

## 2. 准备工程与设备

1. 在自己的干净工作区切换到 `harmony/mobile-scheduler`，拉取最新内容；已有未提交改动先妥善保存，不要覆盖。
2. 使用 DevEco Studio 打开 `harmony-agent/apps/harmony`。当前工程目标为 HarmonyOS 6.0.2 / API 22、Phone；先核实测试机与本机 SDK 的兼容性。
3. 使用自己的开发账号/证书完成签名，选择手机运行 entry。开发侧生成的 `entry-default-unsigned.hap` 未签名，不能据此宣称可安装通过。不要把签名私钥、密码或个人证书提交到 Git。
4. 开启手机开发者调试并授权电脑。使用 SDK 内的 `hdc list targets` 确认设备出现；如用 DevEco Run 安装，保留安装与启动结果。
5. 本地可先运行构建及主机测试（路径自行替换）：

```powershell
cd <仓库目录>/harmony-agent
./scripts/native-check.ps1 -StudioHome '<DevEco Studio安装目录>' -Task all
python ./scripts/test-phone-summary.py
```

首次加载会导入 2700 条本地数据、加载模型和执行模型自检。等待首页加载完成和后台预热结束，再开始正式实验。模型/数据加载失败应记录日志，不将空结果视作通过。

- 2700 条数据可能运行很快。如果 F07/F08 难以观察，保留原始日志并标记证据不足；不要加入人工等待冒充模型耗时。分块、公平性、状态过期和停止槽位协议另有主机回归测试。
- 品牌硬过滤目前支持耐克/Nike、阿迪达斯/Adidas、华为/Huawei、苹果/Apple、联想/Lenovo，基于标题别名；不是品牌实体识别模型。价格支持“预算 N”“N 元以内/以下”“至少 N”“N 元以上”和“A 到/至/- B 元”。不要把任意自然语言条件都当成已支持。
- 无法立即中断的推理可能短暂保持 STOP_REQUESTED；这不等于资源已释放。若长期不退出，请附开始/停止时间和日志。
- 不必为了测试让手机实际过热；保护逻辑使用明确标记的注入实验验证，与真实性能数据分开。

## 5. 正式对照实验操作

1. 清除调试注入，确认状态来源 REAL，恢复全局调度，等待已有任务结束。若存在手动暂停任务，先恢复并等待完成。初始化未完成或队列非空时实验会拒绝启动。
2. 打开调度面板的“真实负载对照实验”，点“运行真实对照实验”。不要使用下面的模拟探针作为性能实验。
3. 保持应用前台，不切策略、不注入状态，不同时手工搜索。代码会自动执行：
   - 固定性能、固定省电、自适应三种模式；
   - 有后台缓存竞争、无后台竞争两组；
   - “运动鞋”“耐克500元以内”“华为”三条查询；
   - 每组重复三次，并轮换模式及有无后台的执行顺序。
4. 正常结束应有 **54 条搜索记录**，其中 27 条带后台任务。失败、取消、过期也应保留，不是只导出成功样本。
5. 点“导出实验 JSON”，使用系统文件选择器保存 `phone-时间戳.json`，复制到电脑。不要仅拍截图代替原始文件。
6. 记录当次环境与文件名。建议不同时间重复至少三次完整会话，保存每次原始结果；不要覆盖前一次数据。

后台任务在前台搜索结束后最多再等待 10 秒便请求取消，避免热保护暂停使整场实验无限等待；底层实际退出仍需确认。此类后台样本记为取消，不算后台成功吞吐。若某个不可中断调用一直不结束，导出会等待实验结束，请保留系统日志作为故障证据。

如果中途停止/出错，记录数可能少于 54，JSON 中会记录 cancelled/error。应单独分析，不和完整会话混成正式结论。

## 6. 电脑汇总

在 `harmony-agent` 目录运行：

```powershell
python ./scripts/summarize-phone-experiment.py '<导出的phone文件.json>' --output '<汇总文件.csv>'
```

脚本按模式、有无后台、样本阶段和状态来源分组，输出：

- 成功率、所有终态的 P50/P95、仅成功任务的 P50/P95；
- 各节点排队时间之和的均值、截止时间违约率；
- 后台成功样本数及每秒完成行数；
- 有独立标注时的 Recall@20、返回结果精确率。

“首个会话样本”不等于真正冷启动：初始化已经加载模型，其他线程配置可能在后续第一次使用时才加载。脚本将首个与后续样本分组，但不声称后续全部是预热稳定态。正式报告要额外记录进程重启和模型预热条件；需要严格冷启动实验时单独记录初始化时间，不与这 54 条搜索混算。

注入或缺少来源证据的样本会单独分组。若 `droppedEvents > 0`，汇总脚本拒绝处理，需缩短会话或修复采集。事件上限为 20000，独立于 SDK 最近 500 条日志窗口。

## 7. 质量评测

不能把余弦相似度当作检索准确率，也不能用系统自己返回的结果直接充当正确答案。

1. 使用当前版本的商品语料，由同学独立判断哪些商品与每条查询相关，并满足品牌/价格条件。
2. 按 `docs/testing/phone-quality-labels.example.json` 格式填写相关商品 externalId。空列表表示未标注，不进入质量统计。
3. 运行：

```powershell
python ./scripts/summarize-phone-experiment.py '<实验.json>' --labels '<人工标注.json>' --output '<含质量的汇总.csv>'
```

只有真正独立标注的查询才会计入质量结果。失败查询按未命中计算，不从质量统计中悄悄删除。原始事件包含检索节点的 modelTier/qualityLevelId，可核对当前维度档位；若本机状态使所有模式选择同一档，应如实报告，不能强写出降维对比。

## 8. 哪些观察不能直接下结论

- 线程遥测表示传入 MindSpore 的线程配置或 TaskPool 分区数，不是操作系统实际并行线程采样。
- `serial_fallback` 表示检索回退串行路径；这种样本不能当成原计划多分区执行。异常需一并报告。
- 电量百分比、预测 relativeEnergyCost、热风险分数都不是功耗仪数据。
- 自适应不保证每个场景都最快；应结合质量、前台延迟、后台完成率与资源状态解释取舍。
- 后台公平性表示可运行任务等待 30 秒后优先获得下一空闲槽位；不会抢占当前不可中断计算，也不会越过保护暂停。
- V1 未实现速率预算型限流。过去的 THROTTLE 输出已撤销；需要保护却不能暂停的旧后台任务会被拒绝。不要把此行为写成已实现硬件降频。
