# 实时调度仪表盘与提问诊断

日期：2026-09-22。分支：harmony/mobile-scheduler。范围：harmony-agent/apps/harmony。

## 本轮要求与问题核查

用户要求在操作 App 时同时打开调度仪表盘，使用提供的 HTML 前端呈现真实调度信息，并核查为什么需要调整初始参数时没有出现选择题。

实际发现的原型路径是 `调度盘/code.html`，同目录包含 DESIGN.md 与 screen.png。原型用随机数和定时抖动演示开发板 CPU/NPU、功率、线程亲和性及云端状态，没有连接手机调度服务。这三个文件保持原样作为设计来源。

此前实现确实有缺口，不能把“有反馈组件”视为完整链路：

- 顶部控制台入口使用路由跳转，触发购物页 onPageHide 和 PAGE_LEFT，会取消正在查看的任务，无法边搜索边观察同一任务。
- 只实现了成功结果展示后的低频体验反馈，没有首次任务参数确认。反馈默认关闭；未授权、未成功、未展示、同类任务当天已询问等条件返回 null，页面没有解释原因。
- 模拟器连续搜索又复现了输入框程序清空触发 onChange 的问题：被误判为用户改需求，取消刚提交的任务，导致没有成功结果可供反馈。本轮增加当前草稿值相等判断，程序同步不触发取消，真正修改输入仍使旧请求失效。

## 仪表盘数据链路

```text
设备适配器 -> SchedulerService 的设备状态、任务队列、执行计划与执行器遥测
          -> getDeviceState / getMetricsSnapshot / getActiveTasks / getRecentLogs
          -> SchedulerLiveFeed（只读快照、状态/日志订阅、500 ms 心跳）
          -> SchedulerDashboard 原生组件
          -> Index 当前购物页内展开，上下分区同时操作
```

保留原型深色、金色与绿色的仪表风格，按手机实际采集能力重构为原生 ETS，不使用 WebView 或随机数。打开、关闭和冻结画面不路由离页、不发送 CANCEL/PAGE_LEFT、不暂停调度；冻结仅停止画面替换，恢复后读取最新快照。日志事件合并刷新间隔为 100 ms，短任务的 RUNNING 与终态仍可从近期事件查看。最近展示 24 条事件，底层仍使用现有有限日志窗口，不宣称无限留存。

| 展示 | 真实来源和限制 |
|---|---|
| 电量、CPU、可用内存、热状态 | 当前设备状态；未知显示 `--`/UNKNOWN，保留 REAL/INJECTED/MIXED 来源；热级别不冒充摄氏温度 |
| 运行、排队、暂停、窗口 P95 | SchedulerService 当前队列及终态窗口统计；无完成样本不显示虚构 P95 |
| 活动任务、目标/截止时间、高质量要求 | 新增 ActiveTaskSnapshot，来自实际已提交任务；无业务原文、图片或输出 |
| 计划配置、实际配置、原因、耗时 | 调度日志与执行器 actual 遥测分列；未确认不冒充实际执行，保留策略模式和保护原因 |
| 反馈与参数回执 | 同任务 telemetry.feedbackReceipt；是否校准由 SDK 回执判定 |
| NPU/GPU 利用率、功率、云 RTT | 本手机路径尚无采集数据，明确不展示原型模拟数字 |

快照为脱离内部对象的拷贝，UI 不能通过修改配置引用影响运行任务。读取失败或调度器未初始化时显示未连接，不保留旧值冒充实时数据；组件退出解除监听与定时器。500 ms 是展示刷新频率，不是每个传感器的采样频率；资源字段仍遵守既有 TTL 和未知状态保护。

“策略与实验控制台”仍是原有独立调试页面，主动进入该页面仍遵守离页取消协议。边搜索边观察请使用当前页的仪表盘，不通过实验控制台跳转。

本轮默认交付为**手机 App 内实时仪表盘**。原始 HTML 本身仍是设计原型，直接用电脑浏览器打开它不会读取手机数据。本轮没有新增跨设备 WebSocket、手机遥测上传或浏览器远程控制接口；后续若需要大屏观看，可以在只读快照边界增加显式授权、鉴权及断连处理的传输适配器，不能直接把旧 Web 后端的数据冒充手机数据。

## 结果后的低频体验题

此前的“速度/质量平衡、300/500/800 ms”首次参数题已撤销。它把内部调度概念交给普通用户判断，体验不合理；当前搜索直接采用 App 的保守默认约束，用户不需要理解目标时延、模型档位或执行配置。`SearchPreferences` 仍保留为内部兼容的 TaskContext 构造能力，但没有对应的普通用户弹窗。

用户进一步明确：温度、内存占用和卡顿属于应自动观测的客观信息，不应询问用户。最终方案撤掉发热/卡顿题；指标缺失时保持未知并遵守既有保守调度，不用问卷代替采集。内存占用不能直接等同于卡顿，精确卡顿仍需要帧耗时/掉帧遥测；当前未接入完整帧卡顿采集，不宣称已实现。

用户只在授权后、成功结果已经展示且存在相关迹象时看到一题主观判断。调度器先读取 App 上报的结果展示/消费、任务耗时与可选应用观测，再按下表选择；没有必要就不提问：

| 优先级 | 条件 | 用户看到的问题 | 选项 |
|---|---|---|---|
| 80 | 调度耗时或 App 测得的结果准备耗时超过任务软截止；时长已知，但用户容忍度未知 | 刚才等待结果的时间可以接受吗？ | 很快 / 能接受 / 有点慢 / 一直没出来 |
| 40 | App 明确报告结果质量不确定，且未报告有用性、用户尚未消费结果 | 这次结果符合你的需求吗？ | 有用 / 不够准确 / 无关 |
| 不出题 | 正常完成、无明确质量疑点，或应用已提供所需判断 | 无 | 无 |

一次只问一个问题；“稍后回答”收起，不会当作满意或不满意。进入商品详情时隐藏题目。等待容忍度和结果需求符合度独立校准，不把实际耗时直接当作用户不满意，也不把一次点击直接当成正面训练标签。客观设备保护无需等用户作答。

通用 `TaskSignal.experience: AppExperienceObservation` 是可选字段，不依赖购物页面或商品类型：

- `responseReadyMs`：App 从提交到结果交给页面的实测耗时，与 SDK 执行耗时分开保存，不冒充屏幕实际出帧时间。
- `resultQualityUncertain`：应用确有质量疑点时主动上报；不能拿资源预测置信度或随机分数冒充结果置信度。
- `resultUseful`：应用已有明确判断时上报；未提供不填 false。已有判断或 RESULT_CONSUMED 可抑制不必要的质量题，但不会替用户填写问卷。

只有成功任务的 RESULT_DISPLAYED / RESULT_CONSUMED 信号接收这些字段；数值经过有限性和范围校验，布尔值校验类型，只复制白名单，不记录业务原文。当前购物 App 只上报真实 `responseReadyMs`，**未伪造质量置信度或强制置为不确定，因此常规路径仅在等待超出预期时询问容忍度**。质量题接口已由合成用例验证，后续接入真实质量判断后才会按条件启用。新增字段不改既有硬约束或直接下发执行参数。

```text
成功结果 -> RESULT_DISPLAYED -> getFeedbackAvailability(workflowId)
  -> getFeedbackRequest -> 页面单题 -> submitFeedback
  -> 校验工作流/同意/有效期/选项/重复 -> 有界校准或积累 -> 回执
```

新增只读 FeedbackAvailability。SDK 按工作流所有权映射到输出节点，返回 READY 或明确原因。反复读取状态不生成邀请、不消耗提问次数。仪表盘显示未授权、等待完成、未成功、未展示、无需提问、已回答、邀请过期、同类今日已询问、日总上限或间隔不足等原因，并在事件中展示邀请的 selectionReason 和提问优先级。结果出来之后再授权，可以尝试获取符合条件的邀请，并非必定弹题。

保持既有频控：UTC 日最多 2 次，同能力/任务类型每天最多 1 次，两次至少间隔 30 分钟，邀请 2 分钟过期。因此，同一购物检索当天连续测试通常只有一次结果体验题，这是原保护规则，不是弹窗故障。系统不会为了轮询更多维度而突破频控。

回答仍走文档 12 的 FeedbackReceipt 和受约束校准。时延、结果质量各自达到默认最少 10 条才可能校准，同配置/版本/状态桶隔离，样本仅进程内；普通短会话多为 COLLECTING，**没有完成持续跨启动学习或神经调度模型训练**。一次回答只产生有界样本，不直接改线程数、模型档位、质量底线或硬截止。页面回执只告诉用户“已记录/积累后再调整/继续经过安全边界”，不展示内部权重。小高度内容区改为可滚动内嵌题目，避免仪表盘展开后浮层被裁掉；常规高度保留浮层。历史 DEVICE_COMFORT 枚举为接口兼容保留，当前自动邀请不会产生此类问题。

## 验证与复测步骤

自动化覆盖简单提问文本与选项、等待容忍度优先于质量疑点、客观指标异常或缺失不产生客观问卷、App 观测校验和拷贝、无必要不消耗配额、不把消费当正面反馈、任务所有权、限频和过期、实际活动任务快照及防修改、监听销毁、延迟初始化、未知数据和读取失败。最新执行结果见阶段记录中的阶段九及 testing 下的原始测试报告。

最终改题后的主机回归已通过：scheduler 160、entry 26、Python 9 项，无失败或忽略；HAR 和未签名 HAP 构建成功。当前 hdc 为 `[Empty]`，尚未完成最终版本的设备 UI 复测。旧初始题截图已删除，其余截图明确标记为历史。构建结果、复现细节与产物哈希见 [本轮验收](testing/08-live-dashboard-and-questions.md)。

建议在目标手机逐项复测：

1. 直接输入商品并发送，不应出现内部时延参数题；搜索仍采用保守默认约束。
2. 打开顶部右侧的“调度盘”按钮，再发起搜索；确认同页任务能完成，日志显示 prepare/encode/retrieve 的实际事件，而非开面板即 PAGE_LEFT。
3. 开启本地体验反馈，符合频控且等待超过预期的成功搜索出现等待容忍度问题；正常快速搜索不出题。回答回执与相同输出 taskRunId 对应，后续同类邀请仍受日限额限制。
4. 高温/低内存仍自动走设备保护，不问温度、内存或卡顿；质量不确定通过测试信号验证，且低于等待容忍度问题优先级。选项不出现目标时延、模型档位等术语。
5. 收起/恢复、过期、撤销授权、改输入、换页、切后台时，旧邀请不能套用新任务。小屏、键盘、大字体和展开仪表盘时，问题与操作按钮均可到达。
6. 模拟器的硬件状态可用性和性能不代表真机。真实手机还需验证传感器、MindSpore 推理、热保护、质量和收益，不以逻辑测试或构建成功替代。
