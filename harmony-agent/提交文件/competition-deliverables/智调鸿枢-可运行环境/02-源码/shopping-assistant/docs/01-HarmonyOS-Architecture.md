# 端云协同 AI 任务感知调度中间件架构设计

## 文档信息

- 项目：面向鸿蒙应用生态的端云协同 AI 任务感知调度中间件
- 演示应用：SoleAI 智能比价购物助手
- 架构版本：1.1
- 状态：当前有效
- 基线日期：2026-07-25
- 上位基线：`00-项目统一口径与开发基线.md`

## 0. 1.1 版纠偏规则

1. 本地 Embedding、2700 条商品向量检索和前后台任务仲裁是必须可离线工作的核心能力。
2. 云端 LLM 只负责可选答案生成，不参与商品事实判定；云端失败不得清空本地结果。
3. 任务同时按 `TaskType` 和已实现的 `InferenceLocation` 分类。远端计划禁止携带 CPU/GPU/NPU 和线程数。
4. 当前 `LocalAiModelEngine`、MindSpore Provider 和 Cloud Provider 均为原型或 Stub，不得描述成真实模型或真实云端调用。
5. 当前默认 GPU/NPU 可用列表不是能力探测结果；未完成真实执行器探测前只允许将 CPU 视为已知可用后端。
6. 本文后续章节中与本节冲突的旧端侧纯本地表述，以本节和 `00-项目统一口径与开发基线.md` 1.1 版为准。

## 1. 架构目标

系统在不修改操作系统底层、不依赖 root 权限的前提下，为 HarmonyOS 应用提供可复用的端云协同 AI 任务调度能力。调度器对本地 Embedding、向量检索和索引维护选择模型档位、真实可用后端、CPU 线程档位及任务优先级；对远端答案生成选择 Provider、超时、有限重试、并发和降级策略，使应用在结果质量、响应速度、热稳定性、续航与网络可用性之间动态平衡。

架构必须满足以下约束：

1. 最终主入口是 HarmonyOS 原生 ArkUI 应用。
2. 购物主链路在离线状态下可运行。
3. 调度策略不依赖某一个具体模型或商品品类。
4. NPU、QoS、热档位等能力必须通过真机验证，且都存在降级路径。
5. 调度库与演示 App 分离，最终以 HAR 交付。
6. 本地 Top-K 是商品事实来源，云端答案生成是可选增强，不得成为本地主链路的前置条件。
7. 远端任务不得携带或展示端侧 Backend、线程数和模型档位。

## 3. 模块边界

| 层级 | 主要模块 | 输入 | 输出与责任 |
|---|---|---|---|
| 演示应用层 | 页面、组件、导航、调度面板 | 用户图片、文字、筛选操作 | 展示业务结果和调度状态，不实现策略 |
| HAR 门面层 | SchedulerService、公共类型 | TaskRequest、PolicyMode | 稳定公共 API、生命周期和错误边界 |
| 状态感知层 | DeviceStateMonitor、状态适配器 | 系统 API、调试注入、耗时窗口 | 统一 DeviceState 快照 |
| 策略决策层 | SchedulerPolicy、HysteresisController | DeviceState、TaskProfile | ExecutionPlan 与可解释原因 |
| 任务执行层 | TaskQueue、ExecutorRegistry | ExecutionPlan、任务载荷 | 排队、取消、执行、超时和结果回传 |
| Native 推理层 | NAPI/C++、MindSpore Lite | 模型、张量、线程档位 | 真正的端侧推理结果和耗时 |
| 本地数据层 | RelationalStore、本地索引 | 商品数据、查询条件、向量 | 商品检索、筛选、排序和持久化 |

## 4. 演示应用层

### 4.1 页面组成

- `Index.ets`：正式首页，提供文字、样例图、相册和相机入口。
- `ResultsPage.ets`：本地商品结果、筛选、排序和分页。
- `ProductDetailPage.ets`：商品详情、平台、价格、库存和推荐说明。
- `SchedulerPanelPage.ets`：设备状态、策略、队列、日志和实验模式。

页面只调用业务服务和 HAR API，不直接访问系统状态 API，不直接选择模型或线程数。这样可以防止演示逻辑与调度能力耦合，并确保 HAR 可以被其他应用接入。

## 5. HAR 调度中间件

调度器应从 `entry` 中分离为独立 HarmonyOS Library：

```text
scheduler/
├── api/             # SchedulerService、SchedulerTypes
├── state/           # DeviceStateMonitor、状态适配器
├── policy/          # SchedulerPolicy、滞回控制
├── queue/           # TaskQueue
├── executor/        # ExecutorRegistry
└── observability/   # SchedulerLog、MetricsWindow
```

### 5.1 任务模型

任务分为三类：

1. `FOREGROUND_REALTIME`：拍照识别、用户点击搜索等直接影响界面响应的任务。
2. `USER_INITIATED`：商品详情分析、相似商品推荐等用户明确触发的任务。
3. `BACKGROUND_BATCH`：商品索引重建、缓存刷新和离线批处理。

每个任务携带时延目标、精度偏好、是否允许降级、是否允许暂停和最大执行时间。

### 5.2 调度输出

策略引擎已按 `InferenceLocation` 输出判别联合计划：本地计划包含模型版本、1/2/4 CPU 线程档位、真实可用 Backend、队列动作、原因和策略版本；远端计划包含 Provider、超时、有限重试、并发等级和降级许可，禁止出现 CPU/GPU/NPU 与线程数。

## 6. 状态感知设计

| 字段 | 来源 | 不可用时处理 |
|---|---|---|
| 电量百分比 | HarmonyOS 电池公开 API | 标记 unknown，不因缺值自动高性能 |
| 充电状态 | HarmonyOS 电池公开 API | 标记 unknown，按未充电保守处理 |
| 热档位 | HarmonyOS 热管理公开能力 | 使用耗时趋势和调试注入辅助 |
| 应用前后台 | UIAbility 生命周期 | 默认按前台处理用户当前操作 |
| 近期推理耗时 | MetricsWindow | 无历史时使用模型基准值 |
| 队列深度 | TaskQueue | 必须可用 |
| NNRt/NPU 能力 | 真机能力枚举 | 不可用则只注册 CPU 执行器 |

真实状态和调试注入必须经过同一个状态归一化入口。日志必须标记 `REAL` 或 `INJECTED`，避免把模拟状态误写成真机实验结果。

## 7. 策略设计

| 档位 | 进入条件示例 | 执行计划 |
|---|---|---|
| 高性能 | 热状态正常，且电量充足或充电中 | 高精度模型、4 线程、前台优先 |
| 均衡 | 轻微发热、电量中等或队列升高 | 均衡模型、2 线程、后台限速 |
| 省电/保护 | 高热、低电量且未充电 | 轻量模型、1 线程、后台暂停/延后 |

冲突时按“热安全与低电量保护 > 前台实时任务 > 精度偏好 > 后台吞吐”处理。降档立即生效；升档必须等待状态持续稳定，并设置档位最短保持时间。策略只在任务或帧边界切换，不在单次推理中途迁移。

## 8. Native 推理层

Native 层通过 NAPI 向 ArkTS 暴露稳定接口，负责：

1. 加载和预热 MindSpore Lite 模型。
2. 创建 1/2/4 线程推理配置。
3. 执行输入预处理、张量构建和推理。
4. 返回结果、阶段耗时、后端信息和错误码。
5. 处理取消、超时和资源释放。

模型档位优先采用同一任务的不同尺寸或量化版本。若只有一个模型，不能仅通过修改标签伪装成多模型调度。

## 9. 本地数据与图像检索

RelationalStore 保存标准化商品事实。建议新增数值价格、品类、品牌、标签、导入版本和向量引用，并为 `platform + externalId` 建立唯一约束。

当前种子导入目标已扩展为 2700 条商品事实数据，但数据库尚无向量字段，当前查询仍是关键词过滤后对少量候选做原型排序。下一阶段应在开发机离线生成与模型版本绑定的商品向量，并通过独立向量表或经验证的向量存储导入设备；不能把运行时哈希投影描述为预生成 Embedding。

```text
用户图片
→ 自动主体建议或手动框选
→ 裁剪、补边、缩放、归一化
→ 查询 embedding
→ 本地 ANN/近邻检索
→ 结构化筛选和排序
→ 商品结果
```

商品图 embedding 宜离线预计算；设备端重点生成查询 embedding。Grounding DINO、SAM 和 FAISS 等旧方案资产只能作为算法参考，是否进入移动端必须重新评估模型体积、算子支持和性能。

## 10. 关键数据流

### 10.1 前台搜索

1. 页面创建 `TaskRequest`。
2. HAR 读取最新 `DeviceState`。
3. 策略引擎生成 `ExecutionPlan`。
4. TaskQueue 按任务类型与优先级排队。
5. ExecutorRegistry 调用本地检索或 Native 推理执行器。
6. 结果返回页面，同时写入调度日志和滑动指标窗口。

### 10.2 后台任务干扰

1. 后台索引任务以 `BACKGROUND_BATCH` 提交。
2. 前台任务到达时，队列提升前台任务并限制后台并发。
3. 高热或低电量时暂停后台任务。
4. 状态稳定后按滞回规则恢复后台任务。

## 11. 日志与实验数据

每次调度至少记录：任务 ID、任务类型、状态来源、设备状态、模式、模型、线程数、后端、排队时间、推理时间、总耗时、结果质量、命中规则和错误码。

日志用于调度面板和测试报告，但不保存用户原始图片、密钥或其他无关敏感数据。

## 12. 降级与故障处理

| 故障 | 降级行为 |
|---|---|
| 热档位 API 不可用 | 使用耗时趋势，保留调试注入，仅对真实指标做保守说明 |
| QoS API 不可用 | 使用应用内优先队列和并发限制 |
| NNRt/NPU 不可用 | 仅注册 CPU 执行器 |
| 高精度模型加载失败 | 降级到均衡或轻量模型 |
| 本地 ANN 索引不可用 | 退回结构化关键词/标签搜索 |
| 图片自动检测失败 | 让用户手动框选或重新选择图片 |

## 13. 安全与隐私

- 默认在设备本地处理图片、商品数据和推理结果。
- 不在仓库中提交真实 API key、签名材料或账号凭据。
- 调试日志不得包含密钥和完整用户图片。
- 云端答案生成必须取得用户授权，发送最小化的 Top-K 结构化字段，并与本地检索路径分离。
- 云端模型密钥只保存在服务端；客户端不得内置真实密钥。
- 断网、超时或用户拒绝联网时必须使用本地结果和模板说明降级。

## 14. 构建与部署边界

- 当前产品配置：HarmonyOS 6.0.2(22)，Phone。
- 模拟器用于页面、数据库和策略逻辑调试。
- 真机用于热、电量、QoS、NNRt/NPU 和功耗实验。
- Pura 70 HarmonyOS 4.2 与当前工程存在版本差异，必须在真机实验前解决。
