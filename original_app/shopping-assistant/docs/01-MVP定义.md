# MVP 定义（V0）

## 1. 文档目的

本文档只回答一件事：首版到底必须做成什么样，才算最小可用产品成立。

这里讨论的是首版边界，不是完整产品边界。凡是不直接服务于首版主链路的能力，原则上都不进入 MVP。

## 2. MVP 核心目标

首版 MVP 的目标不是覆盖尽可能多的功能，而是完整证明下面这条链路真实成立：

用户拍一双鞋，系统可以返回多平台的价格与货源结果；用户再通过自然语言追加要求，系统可以在连续上下文中更新结果，帮助用户更快收敛到更符合要求的候选商品。

## 3. MVP 主链路

首版必须打通以下主链路：

1. 用户拍摄或上传鞋类商品图片
2. 系统识别并理解当前商品
3. 系统返回多平台候选结果
4. 用户看到价格与货源信息
5. 用户通过自然语言追加筛选要求
6. 系统在保持上下文连续的前提下更新结果
7. 用户能够继续多轮表达需求，直到结果被收敛

如果这条链路不能稳定跑通，首版就不成立。

## 4. MVP 必须具备的能力

### 4.1 输入能力

- 支持用户从拍照或图片上传开始一次查询
- 首版品类限定为鞋类

### 4.2 识别能力

- 能对鞋类商品形成基础识别结果
- 识别结果能够支撑后续多平台检索

### 4.3 检索能力

- 能基于识别结果返回多平台候选商品
- 返回结果中必须包含价格与货源相关信息
- 当前首版对“同款”的要求，以鞋类品类为准，目标是返回严格一致的同款结果

### 4.4 展示能力

- 用户能直接查看候选商品列表
- 列表能够承载价格比较与货源比较
- 首版货源结果至少应明确展示：
  - `有货 / 无货 / 未知`
  - `平台`

### 4.5 多轮筛选能力

- 用户可以通过自然语言继续补充自己的要求
- 系统能根据新要求更新结果
- 更新不是一次性的，而是应支持连续多轮

### 4.6 连续性能力

- 系统要保留当前轮次的上下文
- 用户不需要每次重新上传图片或重新开始筛选

## 5. MVP 明确不做的事情

首版不做以下方向的扩展：

- 不做鞋类之外的品类扩展
- 不做与主链路无关的附加功能堆叠
- 不为了展示复杂度而引入非必要功能
- 不追求完整覆盖完整产品预期中的所有增强能力

首版只证明核心路径成立，不证明所有未来设想已经落地。

## 6. MVP 与完整产品的关系

完整产品预期中可能包含更多能力，例如更强的价格趋势分析、更丰富的建议体系、更完整的本地记忆、更丰富的品类扩展等。

这些能力不要求在 MVP 阶段全部完成，但 MVP 的结构必须允许后续接入，而不是形成推倒重来的局面。

## 7. MVP 验收口径

首版是否成立，不看功能数量，而看以下问题是否都能回答“是”：

1. 用户能否围绕一双鞋发起一次完整查询
2. 系统能否返回多平台的价格与货源结果
3. 用户能否继续用自然语言表达要求
4. 系统能否根据要求更新当前结果
5. 用户能否连续进行多轮交互，而不是每轮重新开始
6. 整个过程是否足够顺畅，能够用于比赛演示

## 8. 当前已确认的 MVP 口径

截至当前版本，MVP 的关键口径已经明确如下：

1. **“全网最便宜”的 MVP 口径**  
   MVP 不承诺数学意义上的“全网最低价”。当前 MVP 的目标是：在已接入的主流平台范围内，尽可能返回更低价候选，并给出该范围内的最低价结果。

2. **“同款”的 MVP 口径**  
   “同款”的定义按品类分别约束。对于当前 MVP 优先实现的鞋类品类，系统目标是返回严格一致的同款结果。

3. **“货源结果”的 MVP 最低表达要求**  
   当前 MVP 只把以下信息作为最低必达项：
   - `有货 / 无货 / 未知`
   - `平台`

   以下信息属于后续增强项，不作为当前 MVP 最低要求：
   - 店铺类型
   - 是否旗舰店
   - 库存状态细分
   - 可信度
   - 店铺属性
   - 是否适合立即下单

4. **MVP 对降级能力的口径**  
   当前 MVP 允许在外部依赖不稳定时，通过 mock、fallback 或最近一次有效结果保证主链路不断。因此，降级能力属于当前 MVP 的组成部分，而不是偏离 MVP 的临时妥协。
