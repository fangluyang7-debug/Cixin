# 评委分发与入口方案（V0）

## 1. 文档目的

本文档用于明确本项目面向评委的最终交付入口形式，回答以下问题：

- 评委通过什么路径接触项目
- 两条前端入口分别如何交付
- Web 展示页承担什么职责
- 安装说明需要控制到什么复杂度
- 抖音小程序在整体交付里处于什么位置
- 两条入口与后端逻辑如何关系绑定
- 当前交付入口的固定约束是什么

本文档只解决“评委如何拿到并开始体验应用”的问题，不替代后续的部署平台选型与运维方案。

## 2. 当前已确认的分发结论

当前已经确认：

1. 不存在线下展示机会
2. 评委需要自行完成进入与体验
3. 当前 MVP 的正式交付入口采用 `APK + Web 展示页 + 安装说明`
4. 项目规划在后续增加 `抖音小程序` 作为第二前端入口
5. 若后续接入抖音小程序，两条前端入口共用一套后端业务逻辑
6. 抖音小程序当前只保留后续入口位，不展开前端技术路线
7. 抖音小程序当前不进入 MVP 交付范围
8. 当前 MVP 的入口托管基线采用 `Zeabur 静态服务 + 国内对象存储（当前默认腾讯云 COS）`

这意味着当前交付目标分成两层：

- `当前 MVP`：让评委尽可能少思考地进入 APK 路线体验
- `后续扩展`：增加抖音小程序作为第二入口

## 3. 为什么采用这一方案

当前采用“首版单主路径 + 后续第二入口预留”，主要基于以下现实约束：

### 3.1 时间可控

相较于 Google Play 上架或 Open Testing，`APK + Web 展示页` 路径不依赖商店审核、测试人数要求和生产访问门槛，整体时间由项目组自己掌控；而抖音小程序则保留为后续可追加的第二入口。

### 3.2 成本更低

这一方案不要求先解决开发者账号、商店资料、测试轨道和上架前置流程，因此首版交付成本更低；同时后续若接入抖音小程序，也可继续复用同一套后端逻辑，避免为了增加入口而复制整套业务服务。

### 3.3 评委入口仍可保持清晰

虽然 APK 安装天然比应用商店多一步，但通过单独的 Web 展示页承载下载按钮、截图和简短说明，仍可以把评委体验路径收束成一个统一入口；抖音小程序则只作为后续可扩展的补充体验路径。

## 4. 入口结构

当前评委入口应按“两层结构”理解：

- 当前 MVP 主路径：`APK + Web 展示页 + 安装说明`
- 后续规划路径：`抖音小程序`

### 4.1 第一层：Web 展示页

这是评委接触 APK 路径时的统一入口，应承担：

- 项目名称与一句话价值说明
- 安卓 App 下载按钮
- 简短安装说明入口
- 核心截图或短流程说明
- 必要时补充备用网址或备用下载入口

如果后续补入抖音小程序，再决定是否需要在展示页显式加入小程序入口说明。

### 4.2 第二层：APK 下载

这是实际安装载体，应满足：

- 文件名可辨识版本
- 下载链接稳定
- 文件更新后能明确区分版本
- 评委无需登录复杂平台或加入测试计划

### 4.3 第三层：安装说明

安装说明应只解决最必要的问题：

- 安卓如何安装 APK
- 若系统拦截，如何允许安装
- 安装完成后如何开始体验

安装说明应尽量短，避免写成长文档。

### 4.4 后续规划入口：抖音小程序

抖音小程序作为后续规划的第二条前端入口，当前定位是：

- 为评委提供一条无需安装 APK 的进入方式
- 在受限场景下作为更轻的体验入口
- 与 APK 路线共享同一套后端业务逻辑

当前不展开：

- 小程序前端技术路线
- 小程序入口跳转细节
- 小程序后续覆盖范围

### 4.5 共享后端逻辑约束

未来如果形成双路径，前提不是“同时做两个前端”，而是：

- 两条入口共用一套后端逻辑
- 核心业务规则、会话语义、筛选语义和结果结构保持一致
- 不允许因为前端容器不同，演变成两套搜索、两套推荐、两套状态体系

## 5. 评委体验主路径

当前建议的评委主路径先固定为一条：

`打开 Web 展示页`
-> `点击下载 APK`
-> `按照简短说明完成安装`
-> `打开 App`
-> `连接线上后端`
-> `完成拍照检索与多轮筛选体验`

后续如果补入抖音小程序，再增加第二条路径：

`进入抖音小程序`
-> `连接同一套线上后端逻辑`
-> `完成小程序端可承载的主链路体验`

当前 MVP 主路径要求：

- 页面跳转层级少
- 文案短
- 入口识别清晰
- 不要求评委提前加入测试组
- 下载按钮明显
- 安装说明极短

后续如果增加小程序路线，额外要求：

- 进入路径简单
- 不依赖评委额外理解“这是另一套产品”

## 6. Web 展示页的职责边界

Web 展示页是 APK 路线的“入口页”，不是完整产品替代品。

它应负责：

- 承载下载入口
- 帮助评委快速理解产品做什么
- 降低安装前的不确定感
- 提供必要但极简的安装指引

它不应负责：

- 替代移动端主体验
- 承担完整业务逻辑
- 承担评委的主要操作链路

如果后续接入抖音小程序，Web 展示页也不应承担小程序的主体验承载职责。

## 7. 安装说明的边界

安装说明建议控制为极简结构，优先覆盖：

1. 点击下载 APK
2. 若浏览器或系统提示风险，允许本次安装
3. 安装后打开应用
4. 首次进入后按引导完成体验

不建议在这里塞入过长的技术说明、权限原理解释或平台差异细节，除非确实会影响安装成功率。

如果后续接入抖音小程序，小程序路线原则上不应依赖这份安装说明才能进入体验。

## 8. 与后端部署的关系

既然当前 MVP 采用 APK 主路径，且后续预留小程序入口，后端部署就必须满足以下条件：

- 后端公网可访问
- 当前 APK App 指向线上服务
- 对象存储为线上可访问形态
- 下载页、APK 与后端服务之间不存在仅限本地网络的依赖
- 若后续接入小程序，小程序也应通过统一接口层访问相同业务能力

因此，分发入口虽然是前台问题，但会直接约束后端与基础设施部署方式。

## 9. 当前不纳入该方案的路径

当前明确不作为首版主路径考虑：

- Google Play 正式上架
- Google Play Open Testing
- 依赖线下讲解的演示方式
- 只给 APK 文件、不提供统一入口页
- 为两条前端分别建设两套独立后端逻辑
- 把抖音小程序误记成当前 MVP 必做项

这些路径未来仍可追加，但不应影响当前交付主线。

## 11. 当前文档结论

到这一层为止，评委入口方案已经明确：

- 正式交付不走应用商店作为主路径
- 当前 MVP 正式交付采用 `APK + Web 展示页 + 安装说明`
- 当前 MVP 的入口托管基线采用 `Zeabur 静态服务 + 国内对象存储（当前默认腾讯云 COS）`
- 抖音小程序是后续规划入口，不进入当前 MVP 交付范围
- 后续若接入抖音小程序，两条前端入口共用一套后端业务逻辑
- 评委入口应优先追求“少跳转、少说明、少额外权限流程解释”
