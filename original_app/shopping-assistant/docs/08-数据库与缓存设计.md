# 数据库与缓存设计（V0）

## 1. 文档目的

本文档用于在当前产品边界、模块边界和技术约束已经明确的前提下，进一步回答以下问题：

- 当前项目哪些数据应进入数据库
- 哪些数据只需要轻缓存或快照复用
- 图片对象存储与数据库之间如何配合
- 首版需要哪些持久化对象
- 哪些完整产品能力当前只预留扩展位，不进入 MVP 落地

本文档讨论的是“存储分工与结构基线”，不是最终 Prisma Schema 文件，也不是某个缓存产品的绑定实现。

## 2. 当前已确认前提

截至当前版本，和本文件直接相关的已确认前提如下：

1. 后端采用 `Node.js + NestJS`
2. 首版主存储采用 `SQLite + Prisma`
3. 当前 MVP 不引入 `Redis` 等独立缓存组件
4. 图片正式存储路线采用 `国内对象存储`，代码层保持 provider-neutral，当前默认腾讯云 COS
5. 当前 MVP 主链路是 `拍照 -> 多平台结果 -> 自然语言多轮收敛`
6. 当前 MVP 评委入口采用 `APK + Web 展示页 + 安装说明`
7. 后端托管平台采用 `Zeabur`
8. 图片压缩主位置放在 `Flutter` 客户端
9. 首版采用“双轨图片”：压缩识别图先走主链路，原图按需补传
10. 当前 MVP 图片上传采用 `服务端中转`
11. Web 展示页采用 `Zeabur 静态服务`，APK 下载文件采用 `国内对象存储（当前默认腾讯云 COS）`
12. `国内对象存储` 采用多个 bucket 分开存储压缩识别图、原图和演示样例图，当前 provider 为腾讯云 COS
13. 当前 MVP 采用 `NestJS` 进程内轻缓存 + `SQLite` 快照 + 固定 fallback 结果承接缓存与恢复
14. 历史价格、用户记忆、配送时效不进入当前 MVP 验收

因此，本文件的数据库与缓存设计必须首先服务于：

- 一次拍照查询的完整会话
- 多轮连续筛选
- 候选池的稳定更新
- 演示与评委自助体验时的结果恢复与降级

## 3. 设计原则

### 3.1 正式状态进入数据库，热点结果进入轻缓存或快照复用

当前项目中：

- `SQLite` 负责正式状态与可恢复状态
- 进程内轻缓存负责热点结果、短期复用和临时会话加速
- 固定 fallback 结果负责演示兜底

缓存不是最终事实来源，数据库才是。

### 3.2 图片本体不进入数据库

图片本体不应进入 `SQLite`。数据库只保存：

- 图片元数据
- 对象存储引用
- 与会话的关联关系
- 图片处理状态

图片文件本体进入 `国内对象存储`，当前默认腾讯云 COS。

### 3.3 首版优先保证“会话可恢复”

对于当前 MVP，最重要的不是把所有未来对象都一次性建全，而是保证：

- 用户发起一次查询后，会话有锚点
- 当前商品画像可恢复
- 当前筛选条件可恢复
- 当前候选结果可恢复
- 中途失败时能回到最近一次有效状态

### 3.4 首版优先采用“快照思路”

当前会话内的数据变化具有明显轮次特征，因此首版更适合：

- 对关键状态采用快照记录
- 避免过早做过细的强归一化拆分

这样更利于：

- 多轮追问回放
- 问题排查
- 结果恢复
- 降级兜底

### 3.5 P2 能力只预留扩展位

当前不应把 `历史价格`、`用户记忆`、`配送时效` 为了“以后要做”而硬塞进首版核心表结构。更合理的方式是：

- 在对象模型和外键关系上预留扩展位置
- 在当前 MVP 中不强行落完整表与完整写入逻辑

### 3.6 当前 MVP 默认以单实例后端为前提

由于首版主存储采用 `SQLite`，因此当前数据库设计默认建立在以下前提上：

- 后端以单实例部署为主
- 线上环境需要持久化磁盘或卷
- 不按多实例并发写数据库来设计

当前这一前提已经进一步收束为 `Zeabur`，因此本文件中的存储设计默认建立在：

- Zeabur 托管 NestJS 服务
- Zeabur Volume 承载 SQLite 数据文件，建议 `DATABASE_URL=file:/data/prod.db`
- 缓存由应用进程内承接，不单独部署缓存服务

之上。

## 4. 存储分工总览

| 数据类别 | SQLite | 轻缓存 | 对象存储 | 说明 |
| --- | --- | --- | --- | --- |
| 查询会话 | 是 | 可选镜像 | 否 | 数据库为正式来源 |
| 图片元数据 | 是 | 否 | 否 | 只存引用和状态 |
| 图片文件本体 | 否 | 否 | 是 | 正式图片存储位置 |
| 商品画像快照 | 是 | 可缓存 | 否 | 数据库保版本与恢复能力 |
| 自然语言轮次记录 | 是 | 可缓存当前轮 | 否 | 便于连续交互与排查 |
| 当前筛选条件快照 | 是 | 可缓存当前生效版本 | 否 | 多轮筛选核心状态 |
| 候选结果快照 | 是 | 可缓存当前候选池 | 否 | 数据库保恢复，轻缓存保加速 |
| 商品详情临时结果 | 可选 | 是 | 否 | 首版建议优先缓存，不要求重持久化 |
| 外部 API 原始快照 | 是，按需 | 是，短期 | 否 | 用于降级、排查与复用 |
| 固定 mock / fallback 结果 | 是，按需 | 是 | 否 | 兼顾演示稳定性 |
| 用户长期记忆 | 预留 | 否 | 否 | 当前不进入 MVP 落地 |
| 历史价格参考 | 预留 | 可选 | 否 | 当前不要求真实能力 |
| 配送时效参考 | 预留 | 可选 | 否 | 当前不要求真实能力 |

## 5. SQLite 设计

### 5.1 SQLite 的职责

当前 `SQLite + Prisma` 在首版中的职责应集中在四类数据：

1. 会话锚点数据
2. 可恢复的关键业务状态
3. 与对象存储的引用关系
4. 演示与排查需要保留的结果快照

换句话说，凡是“丢了会导致当前查询过程断链”的正式状态，都应优先考虑落库。

### 5.2 当前 MVP 建议持久化的核心对象

首版建议至少持久化以下对象。

#### 5.2.1 `QuerySession`

表示一次完整查询会话。

建议至少包含：

- `sessionId`
- `status`
- `stage`
- `startedAt`
- `lastActiveAt`
- `currentProfileSnapshotId`
- `currentFilterSnapshotId`
- `currentCandidateSnapshotId`
- `currentTurnIndex`
- `entrySource`

它是整个数据库设计的主锚点。

#### 5.2.2 `ImageAsset`

表示一次上传或拍照得到的图片元数据。

建议至少包含：

- `assetId`
- `sessionId`
- `assetGroupId`
- `variantType`
- `objectKey`
- `storagePath`
- `publicUrlOrSignedUrlRef`
- `mimeType`
- `size`
- `hash`
- `sourceType`
- `compressionStage`
- `isPrimaryRecognitionAsset`
- `uploadStatus`
- `createdAt`

注意：这里保存的是图片引用，不是图片二进制本体。

当前双轨图片下，建议这样理解：

- `assetGroupId`：把同一次拍摄产生的压缩识别图和原图关联起来
- `variantType`：区分 `compressed_recognition`、`original_source`
- `isPrimaryRecognitionAsset`：明确当前主链路实际使用的是哪一张

#### 5.2.3 `ProductProfileSnapshot`

表示当前会话某一时刻的商品画像快照。

建议至少包含：

- `profileSnapshotId`
- `sessionId`
- `version`
- `category`
- `brand`
- `color`
- `styleTags`
- `genderHint`
- `sceneTags`
- `size`
- `material`
- `confidence`
- `source`
- `createdAt`

这样做的价值是：

- 识别结果被纠正后可形成新版本
- 多轮过程中不会丢失前一个可比较状态

#### 5.2.4 `SessionTurn`

表示一次自然语言追问轮次。

建议至少包含：

- `turnId`
- `sessionId`
- `turnIndex`
- `userMessage`
- `parsedIntentSummary`
- `createdAt`

这里不要求首版把所有模型内部细节都存下来，但至少要能还原“用户第几轮说了什么”。

#### 5.2.5 `FilterSnapshot`

表示某一轮实际生效的结构化筛选条件。

建议至少包含：

- `filterSnapshotId`
- `sessionId`
- `turnId`
- `priceConstraint`
- `timeConstraint`
- `stockConstraint`
- `shopConstraint`
- `styleConstraint`
- `brandOrPlatformConstraint`
- `sortRule`
- `createdAt`

这里建议采用“每次生效生成一条快照”的思路，而不是只维护一个不断被覆盖的单行对象。

#### 5.2.6 `CandidateSnapshot`

表示一次搜索或一次筛选刷新后形成的完整候选池版本。

建议至少包含：

- `candidateSnapshotId`
- `sessionId`
- `profileSnapshotId`
- `filterSnapshotId`
- `sourceType`
- `candidateCount`
- `createdAt`

它的作用是给 `CandidateItem` 提供归属版本。

#### 5.2.7 `CandidateItem`

表示某个候选池中的单个标准化候选商品。

当前已经确认采用“混合结构”：

- 当前主链路一定会使用的字段采用强结构
- 标准化扩展属性保留在 `normalizedAttributes`
- 供应商原始返回结果保留在 `rawPayload`

建议至少包含：

- `candidateItemId`
- `candidateSnapshotId`
- `providerName`
- `providerProductId`
- `title`
- `normalizedBrand`
- `normalizedCategory`
- `price`
- `currency`
- `stockStatus`
- `shopName`
- `shopType`
- `platformName`
- `productUrl`
- `coverImageUrl`
- `rawScore`
- `rankScore`
- `normalizedAttributes`
- `rawPayload`
- `createdAt`

这里建议把“前台当前需要展示的标准化结果”存成可恢复结构，而不是每次都依赖外部 API 重新拉取。

采用混合结构的主要原因是：

- 不同平台采集字段差异大，真实商品数据会逐步注入商品池
- 主链路必须有一组稳定可比较、可筛选、可排序的字段
- 后续新增平台、爬虫或授权 API 时，不需要频繁改动整个表结构

#### 5.2.8 `ExternalSnapshot` 或 `FallbackSnapshot`

用于保存外部能力的可复用快照或降级快照。

建议至少包含：

- `snapshotId`
- `sessionId` 或 `sceneKey`
- `snapshotType`
- `requestHash`
- `payload`
- `source`
- `createdAt`

首版不需要什么都存，但至少要为：

- 模型识别结果快照
- 搜索结果快照
- 固定 mock/fallback 结果

预留明确落点。

### 5.3 当前建议的关系结构

当前更适合采用下面这条主关系链：

`QuerySession`
-> `ImageAsset`
-> `ProductProfileSnapshot`
-> `FilterSnapshot`
-> `CandidateSnapshot`
-> `CandidateItem`

同时：

- `SessionTurn` 归属于 `QuerySession`
- `FilterSnapshot` 可关联 `SessionTurn`
- `QuerySession` 持有当前版本的各类 snapshot 引用

这种结构的优点是：

- 主链路清晰
- 回滚点清晰
- 同一会话内的状态变更有时间顺序

### 5.4 首版建议不必单独落完整用户体系

当前 MVP 不要求完整登录体系，因此数据库设计不必一开始就强绑定完整 `User` 主表。

如果当前阶段需要为未来预留位置，更稳妥的方式是：

- `QuerySession` 允许后续补 `userId`
- `UserProfile`、`UserPreference` 作为未来表预留，不要求当前落完整写入链路

### 5.5 SQLite 写入时机建议

首版建议优先保证以下写入时机：

1. 创建会话时写入 `QuerySession`
2. 上传图片成功后写入 `ImageAsset`
3. 商品识别完成后写入 `ProductProfileSnapshot`
4. 每轮追问后写入 `SessionTurn`
5. 每次筛选条件生效后写入 `FilterSnapshot`
6. 每次候选池刷新后写入 `CandidateSnapshot + CandidateItem`
7. 发生可复用外部结果时，按需写入 `ExternalSnapshot/FallbackSnapshot`

这条链路的目标是：

- 任何关键节点后失败，都能回到最近一个稳定状态

## 6. MVP 轻缓存设计

### 6.1 轻缓存的职责

当前缓存层不应被理解成“第二数据库”，而应理解成：

1. 识别结果短期复用层
2. 搜索结果短期复用层
3. 当前会话热点状态加速层
4. 降级结果与演示兜底加速层

### 6.2 当前建议缓存的数据类别

首版建议优先缓存以下内容：

#### 6.2.1 识别结果缓存

适用场景：

- 同一图片重复识别
- 同一演示图片被反复使用

缓存内容建议为：

- 商品画像结果
- 识别摘要
- 关键标签

#### 6.2.2 搜索结果缓存

适用场景：

- 相同商品画像 + 相近筛选条件重复查询

缓存内容建议为：

- 标准化候选池
- 候选数量
- 排序结果摘要

#### 6.2.3 会话当前状态缓存

适用场景：

- 用户连续多轮追问
- 当前会话重复读取当前快照

缓存内容建议为：

- 当前商品画像快照摘要
- 当前筛选条件
- 当前候选池摘要
- 当前轮次索引

#### 6.2.4 降级与 fallback 缓存

适用场景：

- 外部 API 临时失败
- 演示时需要稳定返回

缓存内容建议为：

- 最近一次有效结果
- 固定演示样例结果
- 可直接返回的 mock payload

### 6.3 当前建议的缓存命名空间

建议继续沿用 `06` 中已收束的逻辑域：

- `recognition:*`
- `search:*`
- `session:*`
- `fallback:*`

在此基础上，当前更具体的 key 形态建议如下：

- `recognition:{imageHash}`
- `search:{profileHash}:{filterHash}`
- `session:{sessionId}:current`
- `session:{sessionId}:candidates`
- `fallback:{sceneKey}`

如果后续需要缓存详情结果，可补：

- `detail:{provider}:{productId}`

### 6.4 当前建议的 TTL 基线

以下 TTL 只作为首版基线，后续可按真实调用成本再调。

| 缓存类别 | 建议 TTL | 说明 |
| --- | --- | --- |
| 识别结果缓存 | `24h` | 演示图片和重复图识别受益明显 |
| 搜索结果缓存 | `10m - 30m` | 避免频繁重复打商品源 |
| 当前会话状态缓存 | `2h - 6h` | 保障连续交互体验 |
| 详情缓存 | `30m - 2h` | 首版不是核心，可偏短 |
| fallback 缓存 | `1d - 7d` | 用于演示稳定性和兜底 |

### 6.4A 当前对缓存持久化的结论

当前已经确认：

- 当前 MVP 不引入独立持久化缓存
- 不额外把缓存层设计为正式数据库

因此当前更合理的理解是：

- 当前缓存的价值在于“提高单次运行期内的热点复用与交互速度”
- 而跨重启恢复能力主要由 `SQLite` 快照与固定 fallback 结果承担

当前更适合作为“值得保留缓存语义”的内容包括：

- `fallback:*`
- 固定 demo 样例结果
- 最近热点 `recognition:*`
- 最近热点 `search:*`

而 `session:*` 更适合作为运行期加速缓存存在，不应被当成唯一可恢复来源。

### 6.5 缓存中不应作为事实来源的数据

以下数据即使进入缓存，也不应只存在于轻缓存中：

- 查询会话正式状态
- 当前生效筛选条件的正式版本
- 当前候选池的正式恢复版本
- 图片元数据与对象存储引用

这些对象应该可从数据库恢复。

## 7. 数据库与轻缓存的协作策略

### 7.1 总体策略：Cache-Aside

当前最适合首版的策略是：

- 读请求优先读轻缓存
- 未命中时回退到 SQLite 或外部能力
- 得到结果后再回写轻缓存

原因是：

- 实现简单
- 易于排查
- 对当前 MVP 足够稳

### 7.2 当前会话状态的写入策略

对于会话关键状态，建议采用：

- 关键状态先落 SQLite
- 再同步刷新进程内当前摘要

不要反过来把轻缓存当成唯一会话状态源。

### 7.3 搜索结果的写入策略

对于搜索结果，建议采用：

1. 命中轻缓存时直接返回
2. 轻缓存未命中时调外部商品源
3. 标准化后写入 `CandidateSnapshot + CandidateItem`
4. 再把当前结果摘要或完整缓存写入轻缓存

### 7.4 降级读取策略

当外部商品源或模型失败时，建议按下面顺序退化：

1. 读轻缓存中最近一次有效结果
2. 再读数据库中的最近一次相关快照
3. 最后读固定 mock / fallback 结果

这样可以最大化利用已经存在的结果。

## 8. 对象存储与数据库的配合

### 8.1 当前原则

数据库存“引用”，对象存储存“文件本体”。

### 8.2 数据库至少应记录的图片引用信息

建议至少记录：

- `assetId`
- `sessionId`
- `assetGroupId`
- `variantType`
- `objectKey`
- `bucketGroup`
- `mimeType`
- `size`
- `hash`
- `compressionStage`
- `isPrimaryRecognitionAsset`
- `uploadStatus`
- `createdAt`

在当前双轨图片策略下，建议最少把图片分成两类：

- `compressed_recognition`
- `original_source`
- `demo_asset`

其中：

- `compressed_recognition` 应优先用于识别、检索和缓存
- `original_source` 不要求每次立即存在，但如果补传，应能和同一拍摄组建立关系
- `demo_asset` 应和真实用户上传数据保持存储隔离

当前已经进一步确认采用“多个 bucket 分开”的组织方式，因此：

- `bucketGroup` 当前更建议直接表达 bucket 类型
- 至少区分：
  - `compressed-recognition bucket`
  - `original-source bucket`
  - `demo-assets bucket`

### 8.3 图片对象命名约定

当前统一采用以下约定：

- bucket 命名模式：`{project}-{env}-{role}`
- 角色固定为：
  - `compressed-recognition`
  - `original-source`
  - `demo-assets`
- 对象 key 前缀固定为：`{yyyy}/{mm}/{dd}/{sessionId}/{assetGroupId}/`

数据库必须稳定记录 bucket 角色、对象 key 与会话关系。

## 9. MVP 落地与后续扩展的边界

### 9.1 当前 MVP 必须实际落地的存储能力

首版至少应实际落地：

- `QuerySession`
- `ImageAsset`
- `ProductProfileSnapshot`
- `SessionTurn`
- `FilterSnapshot`
- `CandidateSnapshot`
- `CandidateItem`
- 基础 `ExternalSnapshot/FallbackSnapshot`
- 进程内识别缓存、搜索缓存、会话摘要缓存与 fallback 缓存能力

## 11. 当前文档结论

到这一层为止，当前项目的存储分工已经可以明确为：

- `SQLite + Prisma` 负责正式状态、会话恢复和关键业务快照
- 进程内轻缓存负责热点结果复用、连续交互加速和降级加速
- `国内对象存储` 负责图片文件本体，当前默认腾讯云 COS
- 当前图片链路以 `Flutter 客户端轻压缩 + 压缩识别图优先 + 原图按需补传` 为基线
- `CandidateItem` 以“核心字段强结构 + `normalizedAttributes` + `rawPayload`”的混合结构为基线

## 12. 后续已实现补充：用户画像长期记忆存储

当前后端已新增跨会话用户画像长期记忆系统，采用 `邮箱密码 + JWT` 账号体系，画像采用“分块 JSON + 索引表”结构。

新增核心表：

- `User`：用户主表。
- `UserCredential`：密码哈希与盐，当前算法为 `scrypt`。
- `QuerySession.userId`：可空字段，匿名 demo 会话不绑定用户，登录态会话自动绑定用户。
- `UserProfileBlock`：长期有效画像块，按 `blockType + scope + payloadJson` 存储。
- `UserProfileIndex`：从画像块中抽取常用查询字段，例如 `excludedPlatform=pdd`、`shoeSize=42`。
- `UserMemoryProposal`：系统从对话中提取出的待确认记忆。
- `UserMemoryAuditLog`：记录画像新增、编辑、删除、确认和拒绝等操作。

当前长期画像写入原则：

1. LLM 或规则提取只能生成 `UserMemoryProposal`。
2. proposal 必须由用户确认后才写入 `UserProfileBlock`。
3. 身高、体重、三围、鞋码、衣服尺码等身体相关字段标记为高敏感。
4. 不保存完整收货地址，只保存城市或区域级配送偏好。
5. 用户画像 schema 与提取规则放在 `services/api-server/src/prompts/user-memory/`，业务 service 不硬编码画像字段说明。
