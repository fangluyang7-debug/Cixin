# 项目结构与目录规划（V0）

## 1. 文档目的

本文档用于把当前已经确认的产品边界、技术方案、存储方案和接口草案，进一步收束为一套可执行的项目目录规划。

这里重点回答的是：

- 仓库根目录应该如何组织
- Flutter、NestJS、评委展示页分别应放在哪里
- 哪些目录当前版本必须实际创建
- 哪些目录只保留结构位，不建议现在就创建
- 后续扩展到抖音小程序时，目录如何平滑插入

本文档讨论的是“目录规划与工程边界”，不是实际脚手架，也不是最终 CI/CD 配置文件。

## 2. 当前已确认前提

截至当前版本，和目录规划直接相关的已确认前提如下：

1. 安卓客户端采用 `Flutter`
2. 后端采用 `Node.js + NestJS`
3. 主存储采用 `SQLite + Prisma`
4. 当前版本不引入 `Redis` 等独立缓存组件
5. 图片正式存储采用 `国内对象存储（当前默认腾讯云 COS）`
6. 后端部署到 `Zeabur`
7. 评委入口采用 `APK + Web 展示页 + 安装说明`
8. Web 展示页采用 `Zeabur 静态服务`
9. 当前版本只做 `鞋`
10. 当前核心链路是 `拍照 -> 商品池召回 + ANN 检索 -> 多平台候选 -> 自然语言多轮收敛`
11. 抖音小程序不进入当前阶段，但后续若接入，应共用同一套后端业务逻辑

因此当前目录规划必须优先服务于：

- 一个移动端客户端
- 一个后端服务
- 一个评委入口静态页
- 一套清晰可维护的文档与样例数据

## 3. 目录设计原则

### 3.1 先服务 MVP，不为未来过度拆包

当前目录结构应先支持：

- Flutter 客户端
- NestJS 后端
- 评委静态入口页
- 文档与样例数据

不应为了未来多端、多团队、多服务，过早拆成复杂 monorepo 体系。

### 3.2 前端入口分开，后端逻辑集中

当前虽然只有 Flutter 进入 MVP，但后续还可能接抖音小程序，因此目录上应体现：

- 前端入口各自独立
- 后端业务逻辑只保留一套

### 3.3 业务结构优先于技术杂糅

后端目录不应只按 `controller/service/utils` 平铺，而应尽量体现：

- 会话
- 图片资产
- 商品理解
- 检索聚合
- 候选池
- 追问收敛
- 建议与详情

### 3.4 文档、样例、脚本单独收口

当前项目不是纯代码仓库。规划中必须给这些内容单独留清晰位置：

- 计划与设计文档
- 演示图片与 mock 样例
- 本地脚本
- 部署辅助文件

## 4. 当前建议的仓库根目录

当前建议采用下面这套根目录结构：

```text
/
  apps/
    mobile-flutter/
    judge-entry-web/
    miniapp-douyin/            # 后续预留，不建议当前创建实际代码
  services/
    api-server/
  docs/
    assets/
  samples/
    images/
    mock/
  scripts/
  infra/
    zeabur/
  .env.example
  README.md
```

这样组织的原因是：

1. `apps/` 能自然容纳当前 Flutter 和后续小程序
2. `services/` 把后端从前端入口中明确分离
3. `samples/` 单独承接商品池样例、导入样本和 fallback fixture
4. `infra/` 单独承接部署配置，不和业务代码混放

## 5. 当前版本建议实际创建的目录

当前建议真正落地创建的目录只有这些：

```text
apps/
  mobile-flutter/
  judge-entry-web/
services/
  api-server/
docs/
  assets/
samples/
  images/
  mock/
scripts/
infra/
  zeabur/
```

当前**不建议**为了“以后可能会做”而立即创建大量空目录：

- `apps/miniapp-douyin/`
- 复杂 `packages/` 共享代码包
- 多环境 IaC 目录树
- 复杂测试矩阵目录

这些都可以等实际进入对应阶段再加。

## 6. `apps/mobile-flutter/` 规划

### 6.1 目录定位

该目录承载当前版本的安卓客户端主工程。

### 6.2 建议结构

```text
apps/mobile-flutter/
  android/
  ios/                         # Flutter 默认会带出，当前不作为交付重点
  lib/
    app/
      bootstrap/
      routes/
      theme/
    core/
      api/
      config/
      constants/
      models/
      utils/
    features/
      capture/
      session/
      candidate_list/
      candidate_detail/
      refine/
      suggestions/
    shared/
      widgets/
      layout/
      state/
    main.dart
  assets/
    images/
    icons/
  test/
  pubspec.yaml
```

### 6.3 目录分工建议

- `app/`：应用启动、路由、主题等全局能力
- `core/`：接口访问、配置、基础模型与通用工具
- `features/`：按业务页面或业务能力拆分
- `shared/`：可复用 UI 组件与通用状态封装
- `assets/`：Flutter 端实际打包使用的图片、图标等资源

### 6.4 当前版本重点 feature

当前版本至少应围绕以下 feature 建目录：

- `capture/`
- `session/`
- `candidate_list/`
- `candidate_detail/`
- `refine/`
- `suggestions/`

## 7. `apps/judge-entry-web/` 规划

### 7.1 目录定位

该目录承载评委入口静态页，不承载主业务逻辑。

### 7.2 建议结构

```text
apps/judge-entry-web/
  public/
    apk/
    images/
  src/
    pages/
    components/
    content/
  README.md
```

### 7.3 目录分工建议

- `public/apk/`：如果后续需要本地开发期放置下载占位文件，可临时使用
- `public/images/`：评委页所需截图、流程图、品牌图等静态素材
- `src/pages/`：入口页、安装说明页、常见问题页
- `src/components/`：按钮、截图区、说明区等展示组件
- `src/content/`：评委导向的文案配置

这里不强行锁死 Web 技术栈。只要求：

- 生成静态站点
- 能部署到 `Zeabur 静态服务`
- 不承载核心业务 API 逻辑

## 8. `services/api-server/` 规划

### 8.1 目录定位

该目录承载当前版本主要后端服务，即 `NestJS` API 服务。

### 8.2 建议结构

```text
services/api-server/
  src/
    main.ts
    app.module.ts
    common/
      config/
      constants/
      exceptions/
      filters/
      interceptors/
      pipes/
      utils/
    modules/
      assets/
      sessions/
      product-profile/
      search/
      candidates/
      turns/
      suggestions/
      details/
      fallback/
    adapters/
      model/
      search-provider/
      storage/
    cache/
      interfaces/
      implementations/
    prompts/
      shoe/
        profile/
        refine/
        suggestion/
    rules/
      shoe/
        filters/
        mappings/
        ranking/
    persistence/
      prisma/
        schema.prisma
        migrations/
      repositories/
    mocks/
      fallback/
      samples/
  test/
  package.json
  nest-cli.json
  tsconfig.json
```

### 8.3 目录分工建议

#### `common/`

放全局通用能力：

- 配置读取
- 全局异常处理
- 响应包装
- 通用工具方法

#### `modules/`

按业务模块拆分，而不是只按技术层平铺。

当前建议至少有：

- `assets/`：图片资源与上传链路
- `sessions/`：会话创建、状态读取、恢复
- `product-profile/`：商品画像与识别结果
- `search/`：聚合搜索调用与检索编排
- `candidates/`：候选池、候选快照、列表读取
- `turns/`：自然语言追问与解析结果落点
- `suggestions/`：建议卡片与主动推荐结论
- `details/`：商品详情
- `fallback/`：降级、mock、兜底

#### `adapters/`

专门承接外部依赖：

- `model/`：VLM / LLM 适配
- `search-provider/`：商品池检索、ANN 召回和后续外部搜索来源适配
- `storage/`：provider-neutral 对象存储适配，当前默认腾讯云 COS

这样后续换外部供应商，不用把改动打散到各业务模块。

#### `cache/`

虽然当前版本不引入独立缓存组件，但仍建议保留缓存抽象目录。

建议至少保留：

- `interfaces/`：缓存访问接口
- `implementations/`：当前进程内轻缓存实现

这样后续重新接 `Redis` 时，不必改动业务模块依赖方向。

#### `prompts/`

按品类组织 Prompt，而不是散落在模块里。

当前只做 `shoe/`，下层建议至少区分：

- `profile/`
- `refine/`
- `suggestion/`

#### `rules/`

按品类组织规则，而不是混成一个大工具文件。

当前鞋类规则建议至少拆成：

- `filters/`
- `mappings/`
- `ranking/`

#### `persistence/`

集中承接持久化相关内容：

- `prisma/schema.prisma`
- 迁移文件
- repository 封装

### 8.4 NestJS 模块内部建议

对于 `modules/` 下的每个业务模块，建议内部遵循相同子结构：

```text
module-name/
  controllers/
  dto/
  application/
  domain/
  infrastructure/
  module-name.module.ts
```

这样做的价值是：

- API 层、编排层、领域层、基础设施层关系清楚
- 后面模块变复杂时，不需要整体重构目录

## 9. `samples/` 规划

### 9.1 目录定位

该目录承载演示与开发阶段的样例输入和 mock 输出。

### 9.2 建议结构

```text
samples/
  images/
    shoes/
    demo/
  mock/
    profile/
    search/
    fallback/
```

### 9.3 使用边界

- `samples/images/`：放演示图片、鞋类测试图片、固定 demo 样例图
- `samples/mock/`：仅放本地开发 fixture、降级 payload 样例，不作为云端真实商品池来源

不要把这些内容塞进：

- Flutter 打包资源目录
- 对象存储正式对象目录
- 后端业务代码目录

## 10. `scripts/` 与 `infra/` 规划

### 10.1 `scripts/`

建议用于放：

- 本地开发辅助脚本
- 样例数据导入脚本
- APK 或静态页构建辅助脚本
- Prisma 初始化脚本

### 10.2 `infra/zeabur/`

建议用于放：

- Zeabur 部署说明
- Zeabur 服务配置示例
- 环境变量清单

当前不建议在还没开始部署前就引入复杂 IaC 体系；先以可读、可执行的部署说明为主。

## 11. 配置文件建议

当前仓库根目录建议至少保留：

```text
.env.example
README.md
```

其中：

- `.env.example`：列出后端、对象存储、模型、商品池/ANN 和可选外部搜索来源的必要环境变量占位
- `README.md`：作为仓库总入口，说明目录结构、启动顺序和文档索引

如果后续前后端配置项明显增多，再考虑：

- `services/api-server/.env.example`
- `apps/mobile-flutter/.env.example`

当前阶段不必一开始就拆太细。

## 12. 当前不建议立即创建的目录

以下目录当前建议先不要物理创建，只在文档中保留扩展位：

- `apps/miniapp-douyin/`
- `packages/shared-sdk/`
- `packages/generated-contracts/`
- `infra/aws/`
- `infra/terraform/`
- `ops/`

原因很简单：

- 这些目录当前不服务于 MVP 闭环
- 现在创建只会增加空壳和维护负担

## 13. 当前建议的实施顺序

如果后面开始真正建项目，目录层建议按下面顺序落地：

1. 建 `services/api-server/`
2. 建 `apps/mobile-flutter/`
3. 建 `apps/judge-entry-web/`
4. 建 `samples/`
5. 建 `scripts/`
6. 最后补 `infra/zeabur/`

这样安排的原因是：

- 后端和移动端是主链路核心
- 评委入口页依赖主链路功能与素材
- 部署说明应建立在基本工程结构已经清楚之后

## 14. 当前文档结论

到这一层为止，当前项目的工程目录规划可以明确为：

- 采用“`apps + services + docs + samples + scripts + infra`”的轻量结构
- `apps/mobile-flutter/` 承载当前安卓客户端
- `apps/judge-entry-web/` 承载评委静态入口页
- `services/api-server/` 承载唯一后端服务
- `samples/` 单独承接商品池样例、导入样本与本地调试数据
- `infra/zeabur/` 单独承接部署说明与配置
- 抖音小程序只保留扩展位，不进入当前实际目录创建范围
