# 测试与验收清单（V0）

## 1. 文档目的

本文档用于把当前已经确认的 MVP 范围、接口骨架、开发顺序与交付形态，进一步收束为一套可执行的测试与验收清单。

这里重点回答的是：

- 当前完整 MVP 应该测什么
- 每类测试的最低通过标准是什么
- 哪些链路属于必须跑通的验收剧本
- 哪些异常与降级场景必须覆盖
- 最终在提交前，项目应满足哪些“可以交付给评委”的条件

本文档讨论的是“项目提测与验收清单”，不是自动化测试脚本本身。

## 2. 当前验收边界

当前测试与验收边界，以以下已确认前提为准：

1. 当前目标是交付**完整 MVP**
2. 当前完整 MVP 包含：
   - P0 全部模块
   - P1 全部模块
3. 当前交付形态包含：
   - 安卓 APK
   - Web 展示页
   - Zeabur 线上后端
   - 腾讯云 COS 图片链路
4. 当前 MVP 不包含：
   - 抖音小程序
   - 历史价格真实链路
   - 配送时效真实链路
   - 无确认自动长期记忆
5. 当前主链路是：
   - `拍照/上传 -> 商品理解 -> 多平台候选 -> 自然语言多轮收敛`

因此，本文档中的“通过”不是指“所有未来设想都已实现”，而是指：

**当前完整 MVP 在既定边界内可安装、可访问、可跑通、可降级、可交付。**

## 3. 当前验收分层

当前建议把测试与验收分成 6 层：

1. 安装与交付层
2. 后端接口层
3. 主链路集成层
4. P1 增强能力层
5. 降级与恢复层
6. 最终评委体验层

只有这 6 层全部过线，才能说当前版本达到“可交付评委体验”的状态。

## 4. 总体验收通过标准

当前版本要被判定为“可提交”，至少需要同时满足以下条件：

1. Web 展示页可以访问
2. APK 可以下载并安装
3. APK 安装后可连接线上后端
4. 用户能完成一次完整鞋类查询
5. 用户能进行至少两轮自然语言追问
6. 候选结果能随追问刷新
7. 商品详情、建议、决策辅助可见
8. 外部依赖失败时，系统仍有可演示降级路径
9. 不需要开发者手工接管环境，评委即可自行完成体验

如果以上任一项不成立，当前版本都不应被判定为“最终可交付”。

## 5. 安装与交付层测试

## 5.1 Web 展示页测试

### 5.1.1 必测项

- 首页能打开
- 页面无明显空白、报错或资源缺失
- APK 下载入口可见
- 安装说明可见
- 项目基本介绍可见

### 5.1.2 通过标准

- 评委第一次打开页面时，不需要额外解释就能知道下一步要点哪里

## 5.2 APK 下载测试

### 5.2.1 必测项

- 点击下载链接后，APK 能正常开始下载
- 下载文件不是损坏包
- APK 文件大小在可接受范围内

### 5.2.2 通过标准

- 至少两台安卓设备或两次独立安装尝试，均能成功拿到 APK 文件

## 5.3 APK 安装测试

### 5.3.1 必测项

- 安装流程可完成
- 首次打开不闪退
- 首次打开后能进入主界面

### 5.3.2 通过标准

- 新装 APK 后，用户可在不接电脑、不改配置的情况下直接进入应用

## 6. 后端接口层测试

## 6.1 P0 接口清单

当前 P0 接口如下：

1. `GET /api/v1/health`
2. `POST /api/v1/assets/images`
3. `POST /api/v1/sessions`
4. `GET /api/v1/sessions/{sessionId}`
5. `POST /api/v1/sessions/{sessionId}/turns`
6. `GET /api/v1/sessions/{sessionId}/candidates`

## 6.2 P1 接口清单

当前 P1 接口如下：

1. `GET /api/v1/candidates/{candidateItemId}`
2. `GET /api/v1/sessions/{sessionId}/suggestions`

## 6.3 P0 接口最小验收

### 6.3.0 `GET /api/v1/health`

必须验证：

- 服务启动后返回 `status: ok`
- 响应结构符合统一 `success / requestId / data / error` 契约

### 6.3.1 `POST /api/v1/assets/images`

必须验证：

- Day 1 可成功登记压缩识别图语义
- Day 3 可用 `multipart/form-data` 通过 `file` 字段提交图片文件
- 返回 `assetId`
- `assetGroupId / variantType / isPrimaryRecognitionAsset` 语义正确
- 上传失败时能返回清晰错误

### 6.3.2 `POST /api/v1/sessions`

必须验证：

- 能基于 `assetId` 创建会话
- 返回 `sessionId`
- 会话初始状态正确

### 6.3.3 `GET /api/v1/sessions/{sessionId}`

必须验证：

- 能返回当前会话状态
- 能返回当前商品画像摘要
- 能返回当前筛选条件摘要
- 能返回当前是否降级

### 6.3.4 `POST /api/v1/sessions/{sessionId}/turns`

必须验证：

- 能接收自然语言追问
- 能触发结构化筛选更新
- 能推动 `currentTurnIndex` 变化
- 响应体直接返回最新候选列表与建议结果，前端可直接刷新 UI

### 6.3.5 `GET /api/v1/sessions/{sessionId}/candidates`

必须验证：

- 能返回候选列表
- 候选项至少包含：
  - 标题
  - 价格
  - 平台
  - 货源状态
  - 商品链接
  - 图片链接
  - 匹配摘要
  - 原始字段
- 列表结果能与会话当前状态一致

Day 1 后端 smoke 脚本：

```powershell
.\scripts\api-smoke-day1.ps1 -BaseUrl http://localhost:3000
```

## 6.4 P1 接口最小验收

必须验证：

- `GET /api/v1/candidates/{candidateItemId}` 能返回详情、推荐理由、决策标签和决策解释
- `GET /api/v1/sessions/{sessionId}/suggestions` 能返回主动推荐结论、建议卡片、候选摘要和下一步收敛选项
- 当自然语言筛选导致无真实候选时，候选列表必须返回 `degraded: true` 和可展示的 fallback 候选

### 6.4.1 `GET /api/v1/candidates/{candidateItemId}`

必须验证：

- 能返回详情结果
- 至少包含：
  - 标题
  - 价格
  - 平台
  - 货源结果
  - 推荐理由或辅助说明

### 6.4.2 `GET /api/v1/sessions/{sessionId}/suggestions`

必须验证：

- 能返回建议卡片
- 建议与当前候选池和当前筛选条件相关
- 不返回明显脱离当前上下文的无关建议

## 7. 主链路集成测试

## 7.1 主链路剧本 A：标准成功链路

### 步骤

1. 打开 APK
2. 上传或拍摄一张鞋图
3. 等待商品理解完成
4. 查看候选列表
5. 输入第一轮自然语言要求
6. 查看结果刷新
7. 输入第二轮自然语言要求
8. 再次查看结果刷新
9. 点击一个候选查看详情
10. 查看建议卡片和决策辅助信息

### 通过标准

- 主链路全程无闪退
- 不需要重新上传图片
- 不需要手动重置会话
- 两轮追问后仍能保持上下文

## 7.2 主链路剧本 B：严格同款链路

### 验证目标

验证鞋类首版“严格一致同款”口径是否成立。

### 步骤

1. 上传一张品牌、款式特征明显的鞋图
2. 获取候选列表
3. 人工检查前几条候选是否明显属于同一款

### 通过标准

- 前列候选不应大量出现明显不同款的近似鞋
- 若存在不确定结果，系统至少不应把明显不一致的款强标为同款

## 7.3 主链路剧本 C：货源最低表达链路

### 验证目标

验证当前 MVP 最低货源表达是否达标。

### 检查项

- 每个候选至少有：
  - `有货 / 无货 / 未知`
  - `平台`

### 通过标准

- 列表中主要候选项不出现货源字段完全缺失

## 8. 多轮收敛测试

## 8.1 追问语义测试

至少覆盖以下追问类型：

1. 价格约束  
   例如：`500 以内`

2. 货源约束  
   例如：`只看有货的`

3. 平台或来源偏好  
   例如：`先看某个平台`

4. 综合约束  
   例如：`500 以内、有货、先给我便宜的`

## 8.2 多轮连续性测试

至少覆盖以下剧本：

1. 第一轮：限制价格
2. 第二轮：继续限制有货
3. 第三轮：继续收窄排序偏好

### 通过标准

- 后续追问是在前一轮基础上收敛
- 不出现每轮都回到初始结果的情况
- `currentTurnIndex` 与实际轮次数一致

## 9. P1 增强能力测试

## 9.1 智能建议测试

必须验证：

- 建议卡片可见
- 建议卡片与当前会话相关
- 至少存在可以帮助用户继续收敛结果的建议

### 不通过示例

- 建议卡片空白
- 建议内容完全固定、与当前结果无关
- 建议动作点击后不产生结果变化

## 9.2 决策辅助测试

必须验证：

- 列表或详情里存在辅助判断信息
- 用户能看出为什么某些结果更值得优先看

当前可以接受的轻量表达包括：

- 推荐理由
- 价格标签
- 货源提示
- 排序解释摘要

## 9.3 商品详情测试

必须验证：

- 用户能从列表进入详情
- 详情页不只是复制列表
- 详情中至少补充一部分判断信息

## 10. 降级与恢复测试

## 10.1 商品理解失败降级

### 验证目标

当商品理解链路失败时，系统是否仍能给出可演示路径。

### 可接受表现

- 返回明确失败状态
- 或进入可解释的降级状态
- 或使用固定样例 / mock 结果完成演示

## 10.2 商品池 / 搜索 provider 不可用降级

### 验证目标

当商品池为空、商品 embedding 不可用或搜索 provider 不可用时，系统是否能给出明确状态，且前端不会卡死。

### 通过标准

- 至少存在明确错误、降级说明或可控样本候选链路
- 前端不会直接卡死在空白页
- 最终真实链路不得把 mock/hash 伪装成真实候选或真实 embedding

## 10.3 会话恢复测试

### 验证目标

验证当前会话状态是否至少可以通过数据库快照恢复。

### 检查项

- 会话创建后，核心快照已落库
- 重新读取会话时，当前状态可恢复
- 不依赖进程内轻缓存才能继续基本流程

## 10.4 图片链路测试

必须验证：

- 压缩识别图上传成功
- `compressed_recognition` 语义生效
- 原图按需补传链路不影响主链路
- 对象存储对象引用与数据库记录一致

## 11. 异常与错误提示测试

至少覆盖以下异常：

1. 图片格式不支持
2. 图片上传失败
3. 会话不存在
4. 会话未 ready 就强行读取候选
5. 搜索 provider 不可用
6. 详情数据读取失败

### 通过标准

- 出现异常时，前端有反馈
- 后端返回错误语义可区分
- 不出现“用户看到一直转圈但没有解释”的情况

提交前必须逐项勾选：

### 12.1 代码与服务

## 13. 当前验收结论规则

当前建议按下面规则判断版本状态：

### 13.1 可开发中

满足：

- 单个模块可跑
- 但主链路未闭环

### 13.2 可联调

满足：

- 主链路大部分节点已接通
- 但 APK、部署、入口页、降级还不完整

### 13.3 可交付

满足：

- 主链路闭环
- P1 模块可见且可用
- 有降级路径
- 线上可访问
- 评委可自行安装和体验

## 14. 当前文档结论

到这一层为止，当前项目的测试与验收基线已经明确为：

- 不只测单接口，而是测完整会话链路
- 不只测成功路径，也测降级与恢复路径
- 不只看代码能跑，还看评委是否能自己下载安装并体验
- 当前完整 MVP 的通过标准，必须同时覆盖：
  - 主链路
  - P1 增强能力
  - 部署交付
  - 降级兜底

## 15. 后续已实现补充：用户画像长期记忆验收

新增用户画像长期记忆后，后端回归至少覆盖：

- 注册、登录、`GET /api/v1/users/me` 均返回统一响应结构。
- 带 JWT 创建 session 时，`QuerySession.userId` 正确绑定；不带 JWT 的旧 demo 流程仍可运行。
- 用户可新增、读取、编辑、删除 `UserProfileBlock`。
- `GET /api/v1/users/me/profile/context?category=shoe` 能返回鞋类任务相关画像，例如鞋码、排斥平台、偏好品牌。
- 用户在对话中明确表达“我平时 Nike 穿 42 码”“以后别给我拼多多”时，只生成待确认 `UserMemoryProposal`，不直接写入长期画像。
- 用户确认 proposal 后写入长期画像与索引；用户拒绝 proposal 后不生效。
- 敏感字段必须带 `sensitivity=high`，并保持确认后才生效。
