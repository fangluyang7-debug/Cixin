# 可插拔设计速览

本文用于快速说明本项目中已经实现的可插拔设计，以及这些设计如何支撑不同业务场景。它可以作为答辩前的快速阅读材料，也可以作为后续替换模型、数据源、存储或检索链路时的操作地图。

## 1. 核心思想

项目不是把某个模型、某个商品平台、某个数据库或某个图片存储服务直接写死在业务流程里，而是采用：

```text
外部能力
-> Adapter / Provider / Port
-> 标准 Contract
-> Core Service
-> Repository / View Adapter
-> API Response
```

核心服务只处理稳定的业务对象，例如商品、会话、候选、筛选条件、向量和批次状态；外部变化由 Adapter 层吸收。这样后续换模型、换数据 API、换对象存储、换向量检索实现时，不需要推倒重写前端接口和主业务链路。

## 2. 为什么这是评分点

可插拔设计体现的是工程可持续性。比赛或课程项目不只看功能是否能跑，还会看系统是否能适应业务变化。本项目的业务变化主要来自四类：

| 变化来源 | 例子 | 当前项目如何隔离 |
| --- | --- | --- |
| 模型变化 | 豆包、DeepSeek、OpenAI-compatible、未来其他视觉模型 | 通过 `MODEL_ADAPTER`、`EMBEDDING_PROVIDER` 和环境变量切换 |
| 数据源变化 | 聚合 API、JSON、Excel、爬虫、平台官方 API | 通过清洗脚本和 `ProductImportAdapter` 转为统一商品契约 |
| 存储变化 | 腾讯云 COS、未来 OSS/S3/本地存储 | 通过 `OBJECT_STORAGE_ADAPTER` 隔离存储实现 |
| 检索变化 | SQLite 内部向量排序、未来 sqlite-vec、Milvus、pgvector | 通过 `ANN_SEARCH_PORT` 隔离 ANN 实现 |

这些设计使项目不只是一个固定 demo，而是一套可以继续扩展的数据和检索系统。

## 3. 已实现的主要可插拔点

### 3.1 商品数据源可插拔

入口位置：

- `scripts/normalize-collected-products.mjs`
- `scripts/prepare-product-pool-all-mixed-upload.mjs`
- `services/api-server/src/modules/product-pool/application/product-import-adapter.interface.ts`
- `services/api-server/src/modules/product-pool/application/standard-product-import-adapter.service.ts`

作用：

不同平台的数据原始字段完全不同，例如京东、淘宝、苏宁、唯品会、闲鱼的标题、价格、图片、详情页链接、店铺字段都不统一。项目先在导入阶段把这些数据统一成 `ProductImportItemV1`，再进入商品池。

替换方式：

如果后续从新的聚合 API 或官方 API 获取商品，只需要新增或修改“原始字段到标准商品字段”的映射，不需要改搜索、会话和前端候选展示逻辑。

核心收益：

- 支持 JSON、Excel、CSV 等高自由度数据导入。
- 已上传商品可以按 `platform + externalId` 去重。
- 原始 `rawPayload` 保留用于追溯，但核心业务不直接依赖它。

### 3.2 商品池与搜索源可插拔

入口位置：

- `services/api-server/src/modules/search/search.module.ts`
- `services/api-server/src/adapters/search-provider/search-provider.interface.ts`
- `services/api-server/src/modules/product-pool/application/local-product-search-provider.service.ts`
- `services/api-server/src/adapters/marketplace/marketplace-aggregate-search-provider.service.ts`

当前绑定逻辑：

```text
PRODUCT_DATA_PROVIDER=local_product_pool -> 使用本地商品池
PRODUCT_DATA_PROVIDER=marketplace        -> 使用聚合搜索适配器
```

作用：

当前主链路使用本地真实商品池，因为商品可以提前清洗、去重、裁剪、向量化和审计。聚合搜索 API 保留为可替换的商品来源或补充来源。

核心收益：

- 比赛演示时可以依赖稳定商品池，减少实时外部 API 波动。
- 如果后续业务需要实时搜索，可以把聚合 API 接到 `SearchProvider`，不改变 App 调用方式。

### 3.3 模型调用可插拔

入口位置：

- `services/api-server/src/adapters/model/model-adapter.interface.ts`
- `services/api-server/src/adapters/model/openai-compatible-model-adapter.service.ts`
- `services/api-server/src/modules/product-profile/product-profile.module.ts`
- `services/api-server/src/common/config/configuration.ts`

作用：

视觉识别、商品打标、候选视觉复核、多轮对话解析都通过模型 Adapter 输出结构化结果。核心服务不直接消费模型自由文本，也不直接拼模型请求。

环境变量：

```text
VISION_PROVIDER
VISION_MODEL_BASE_URL
VISION_MODEL_NAME
VISION_MODEL_API_KEY

CHAT_PROVIDER
CHAT_MODEL_BASE_URL
CHAT_MODEL_NAME
CHAT_MODEL_API_KEY
```

核心收益：

- 可替换视觉模型或对话模型。
- Prompt 和输出 Schema 可以按品类维护。
- 模型不可用时 fail closed，不用 mock 结果伪装真实结果。

### 3.4 Embedding Provider 可插拔

入口位置：

- `services/api-server/src/modules/product-pool/application/embedding-provider.interface.ts`
- `services/api-server/src/modules/product-pool/application/volcengine-doubao-embedding-provider.service.ts`
- `services/api-server/src/modules/product-pool/application/local-gpu-embedding-provider.service.ts`
- `services/api-server/src/modules/product-pool/product-pool.module.ts`

当前绑定逻辑：

```text
EMBEDDING_PROVIDER=volcengine_doubao_vision -> 云端豆包视觉 embedding
EMBEDDING_PROVIDER=local_gpu_worker         -> 本地 image-worker
```

当前生产策略：

```text
PRODUCT_EMBEDDING_KINDS=visual
ANN_EMBEDDING_KIND=visual
QUERY_EMBEDDING_KIND=visual
PRODUCT_IMPORT_IMAGE_TARGET_SIZE=320
```

含义：

后续上传商品默认只生成纯图片 embedding，避免双 embedding 成本过高。项目仍保留 `multimodal` 能力，用于少量演示或后续预算允许时扩展。

核心收益：

- 可以切换 embedding 模型。
- 可以控制生成纯图片向量还是图片+标签混合向量。
- 数据库记录 provider、model、dimension、embeddingKind，避免不同向量混用。

### 3.5 图片预处理可插拔

入口位置：

- `services/api-server/src/modules/product-pool/application/image-embedding-preprocessor.interface.ts`
- `services/api-server/src/modules/product-pool/application/local-gpu-image-preprocessor.service.ts`
- `services/api-server/src/modules/product-pool/application/noop-image-embedding-preprocessor.service.ts`
- `services/api-server/src/modules/sessions/application/query-image-content-adapter.interface.ts`
- `services/api-server/src/modules/sessions/application/query-image-preprocess-adapter.interface.ts`

作用：

用户上传图和商品主图都会进入标准化预处理流程。预处理结果保存 bbox、裁剪策略、输入图尺寸、是否回退原图等元数据。

当前策略：

商品入库图片统一标准化为 `320p`，后续 embedding 基于标准化后的图片生成。

核心收益：

- 图片裁剪策略可以独立优化。
- 用户图和商品图的处理边界清晰。
- 裁剪失败可以记录并回退，不会静默污染搜索链路。

### 3.6 ANN 检索可插拔

入口位置：

- `services/api-server/src/modules/product-pool/application/ann-search-port.interface.ts`
- `services/api-server/src/modules/product-pool/application/ann-search.service.ts`
- `services/api-server/src/modules/product-pool/product-pool.module.ts`

作用：

当前 ANN 实现在应用内完成向量相似度计算和排序。调用方只依赖 `ANN_SEARCH_PORT`，不关心底层是 SQLite、sqlite-vec、pgvector 还是专门向量数据库。

核心收益：

- 后续升级到真正向量库时，只需替换 port 实现。
- 搜索业务仍消费标准 `AnnSearchResult`。
- 可按 `embeddingKind`、provider、dimension 控制检索范围。

### 3.7 对象存储可插拔

入口位置：

- `services/api-server/src/adapters/storage/storage-adapter.interface.ts`
- `services/api-server/src/adapters/storage/tencent-cos-storage-adapter.service.ts`
- `services/api-server/src/modules/assets/assets.module.ts`

作用：

图片本体不进入数据库，而是进入对象存储；数据库只保存 objectKey、bucketGroup、publicUrl、来源 URL 和预处理元数据。

当前实现：

```text
OBJECT_STORAGE_PROVIDER=tencent_cos
```

核心收益：

- 后续可替换为 OSS、S3 或其他对象存储。
- 数据库不会因为图片二进制膨胀。
- APK、商品图、用户上传图、演示素材可以分 bucket 管理。

### 3.8 API 输出可插拔

入口位置：

- `StandardSessionViewAdapterService`
- `StandardCandidateViewAdapterService`
- `StandardProductViewAdapterService`
- `StandardProductBatchViewAdapterService`
- `StandardSearchEventAdapterService`

作用：

业务 service 不直接拼前端响应，而是把数据库对象交给 View Adapter 输出 API 契约。这样移动端、Web 调试页、运维页都可以复用同一套标准视图。

核心收益：

- 后端内部字段变化时，前端 API 可以保持稳定。
- SSE 进度事件、候选详情、商品池管理视图都能独立调整。
- 未来多端接入时不需要复制业务逻辑。

## 4. 数据与核心功能解耦

项目把“数据是什么来源”和“系统要做什么功能”拆开。典型例子是商品入库：

```text
聚合 API / Excel / JSON / 爬虫数据
-> 清洗脚本
-> ProductImportAdapter
-> ProductImportItemV1
-> ProductPoolService
-> Product / ProductImageEmbedding / ProductImportBatch
```

核心功能只关心标准商品是否有标题、价格、平台、图片、详情 URL、品类和 embedding；不关心原始字段叫“商品名称”“标题”“goodsName”还是“title”。这使系统可以从外界导入高自由度真实数据，而不是被某一个采集工具绑定。

## 5. 替换某个能力时怎么做

| 要替换的能力 | 修改位置 | 不应该修改 |
| --- | --- | --- |
| 新商品平台 | 清洗脚本、平台 ID 解析、`ProductImportAdapter` 映射 | 会话、候选、前端展示主流程 |
| 新聚合 API | `SearchProvider` 或数据导入脚本 | App 接口、商品池表结构 |
| 新视觉模型 | `MODEL_ADAPTER` 实现或环境变量 | `SessionsService` 主流程 |
| 新 embedding 模型 | `EmbeddingProvider` 实现和 `EMBEDDING_PROVIDER` | 商品导入接口、候选 API |
| 新图片裁剪方案 | `ImageEmbeddingPreprocessor` 或 Query Image Adapter | ANN 召回和候选展示 |
| 新向量库 | `ANN_SEARCH_PORT` 实现 | 搜索编排和前端读取接口 |
| 新对象存储 | `StorageAdapter` 实现和 env | 数据库实体和业务 service |

## 6. 环境变量与安全边界

项目把可替换能力集中放到环境变量中，避免在代码中硬编码密钥和供应商参数。

重要规则：

- `.env` 保存本地真实密钥，不提交到 Git。
- `.env.example` 只保存变量名和示例，不保存真实值。
- Zeabur 线上环境变量与本地 `.env` 分开维护。
- `MAINTENANCE_API_TOKEN` 只用于商品池导入、删除、回滚、embedding 重建等高风险接口。
- 普通移动端用户接口不需要维护 token。

典型敏感变量：

```text
VISION_MODEL_API_KEY
CHAT_MODEL_API_KEY
EMBEDDING_API_KEY
OBJECT_STORAGE_ACCESS_KEY_ID
OBJECT_STORAGE_ACCESS_KEY_SECRET
MAINTENANCE_API_TOKEN
JWT_SECRET
DATABASE_URL
```

## 7. 当前项目的推荐生产配置

为了控制成本并保证真实数据链路稳定，当前建议：

```text
PRODUCT_DATA_PROVIDER=local_product_pool
EMBEDDING_PROVIDER=volcengine_doubao_vision
PRODUCT_EMBEDDING_KINDS=visual
ANN_EMBEDDING_KIND=visual
QUERY_EMBEDDING_KIND=visual
PRODUCT_IMPORT_IMAGE_TARGET_SIZE=320
OBJECT_STORAGE_PROVIDER=tencent_cos
```

这样可以保证：

- 商品池使用真实导入数据。
- 后续新上传商品只生成图片 embedding。
- ANN 与 query 使用同一种向量类型，避免混用。
- 商品图统一裁剪和标准化为 320p。
- 图片与 APK 等大文件走对象存储，不压垮数据库。

## 8. 答辩时可以这样概括

本项目的核心不是简单调用模型，而是把外部模型、商品数据、图片存储和检索实现都放在可替换边界后面。系统通过 Adapter 和 Port 把不稳定的外部世界转成稳定的内部契约；商品池把真实商品数据沉淀为可搜索、可审计、可回滚的数据资产。后续如果更换模型、接入新平台、替换向量库或调整图片裁剪策略，主要修改 Adapter/Provider，不影响 App 主流程和 API 契约。

## 9. 功能拓展如何体现

项目的功能拓展不是简单“再加几个页面”，而是基于同一套核心链路扩展业务场景。当前链路是：

```text
图片/文本输入
-> 标准化画像与 query embedding
-> 商品池召回
-> 候选快照
-> 自然语言继续筛选
-> 结果展示和跳转
```

这条链路可以迁移到不同商品品类和不同入口。比如从鞋类扩展到数码、家电或服饰时，主要新增品类 schema、Prompt、字段映射和展示字段；商品池、批次导入、图片标准化、embedding、ANN 检索、候选分页和维护接口都可以复用。再比如从 Android App 扩展到 Web 免下载页或小程序时，前端入口变化，但后端会话、商品池和候选 API 仍保持同一套语义。

因此答辩时可以强调：本项目具备合理的业务拓展能力，不是一次性写死的 demo。它可以根据场景替换模型、替换数据来源、扩展品类、扩展前端入口，并继续复用已经沉淀的真实商品数据库。

## 10. AI 任务编排与 Prompt 设计如何体现

项目里的 AI 不是“调用一次大模型返回答案”，而是多个 AI 子任务的工程编排：

```text
主体定位
-> 图片裁剪标准化
-> 商品画像识别
-> 图片 embedding
-> ANN 召回
-> 候选视觉复核
-> 对话意图解析
-> 建议文案生成
```

每个子任务都有自己的输入、输出和失败边界。主体定位输出 bbox；embedding 输出向量和 provider/model/dimension 元数据；对话模型输出 `filterPatch`，而不是直接修改候选结果；建议生成只能基于已有候选事实，不能凭空编造商品。

Prompt 设计也按任务和品类拆分，而不是散落在业务代码中。视觉 Prompt 负责商品画像和主体框，对话 Prompt 负责自然语言筛选，商品打标 Prompt 负责把商品标题、图片和来源属性转成标准标签。模型输出必须进入 Adapter 做结构化校验，核心服务只消费标准 contract。

这体现了两个评分点：

- 工程中 AI 任务具备合理编排，而不是单次 API 调用。
- Prompt 和输出 schema 具备鲁棒性，可按模型、品类和业务场景迭代。
