# 自然语言全云端端到端审计

> 历史基线说明：本文是 2026-06-20 修复前报告。17 类问题修复后的双模式最终结果见 `cloud-natural-language-e2e-audit-2026-06-22.md`，两种模式均为 153/153。

审计日期：2026-06-20  
被测系统：`https://apiserver.zeabur.app`  
结论：153 条真实云端用例通过 57 条，失败 96 条，总通过率 37.3%。

## 1. 链路一致性

本报告不使用本地 API、mock 模型、内部 Service 或直接正则调用。所有用例均从软件实际使用的云端 HTTP 边界进入：

1. 使用 Flutter `ShoppingApiClient` 相同的移动端固定账户自动登录流程。
2. 初始文本使用 `POST /api/v1/sessions/text`。
3. 请求体使用移动端相同的 `message` 与 `entrySource=android_app`。
4. 多轮筛选使用 `POST /api/v1/sessions/:sessionId/turns`。
5. 请求携带与移动端相同的 Bearer Token，单请求超时 60 秒。
6. 用例顺序执行，间隔 1.5 秒；测试用例请求不重试，5xx 会保留为真实失败。
7. 云端 5xx 后，测试框架只等待健康检查恢复再继续后续用例，不用本地结果补齐。

需要区分“云端链路”和“云模型调用”：用户请求全部经过云端，但云端后端自身会选择本地 fast path、云模型或本地 fallback。该选择也是当前用户真实链路的一部分。

## 2. 总体结果

| 测试层 | 用例数 | 通过 | 失败 | 通过率 |
|---|---:|---:|---:|---:|
| 初始输入与搜索路由 | 35 | 10 | 25 | 28.6% |
| 单轮意图与筛选 | 90 | 34 | 56 | 37.8% |
| 受控多轮工作流 | 16 | 3 | 13 | 18.8% |
| 筛选状态安全 | 6 | 5 | 1 | 83.3% |
| API 输入边界 | 6 | 5 | 1 | 83.3% |
| **合计** | **153** | **57** | **96** | **37.3%** |

HTTP 结果：

| HTTP 状态 | 数量 | 通过 | 失败 | 说明 |
|---|---:|---:|---:|---|
| 201 | 142 | 53 | 89 | 请求完成，但大量语义与状态错误 |
| 400 | 4 | 4 | 0 | 缺失、空白、错误类型正确拒绝 |
| 500 | 3 | 0 | 3 | 云端内部错误 |
| 502 | 4 | 0 | 4 | Zeabur Bad Gateway |

153 条目标请求的响应时延：平均 6.7 秒，P50 6.0 秒，P90 13.5 秒，P95 17.1 秒，最大 48.6 秒；35 条超过 10 秒。

## 3. 实际解析路径

| provider | 用例数 | 通过 | 失败 | 说明 |
|---|---:|---:|---:|---|
| `local_conversation_fast_path` | 42 | 16 | 26 | 云端后端的确定性快速规则 |
| `openai_compatible_chat` | 57 | 20 | 37 | 云端聊天模型真实参与 |
| `local_conversation_fallback` | 7 | 1 | 6 | 云模型输出无法解析后的降级 |
| 未暴露 provider | 47 | 20 | 27 | 初始会话、状态与边界响应 |

7 条 fallback 中，云模型返回了截断或不完整 JSON，例如 `Unexpected end of JSON input`、`Unterminated string in JSON`。受影响输入包括 `不看咸渔`、`白色别来`、`500左右`、`按销量最高排序`、`换一批`、`改回上一个条件`。

## 4. P0：明确违背用户指令

### 4.1 否定语义反转

| 输入 | 期望 | 云端实际结果 |
|---|---|---|
| `不买了` | 停止搜索 | 启动综合商品搜索，返回 117 个候选 |
| `别给我推荐鞋` | 不推荐鞋 | 启动鞋类搜索，返回 117 个候选 |
| `I don't want shoes` | 不搜索 | 启动鞋类搜索 |
| `不要500以上的` | `priceMax=500` | `priceMin=500` |
| `不要求有货` | 取消仅有货 | `stockOnly=true` |
| `不用包邮` | 取消包邮限制 | `freeShippingOnly=true` |
| `不要旗舰店` | 排除旗舰店 | `shopType=flagship` |
| `不要最便宜的` | 不按最低价 | `sortRule=price_asc` |

这些输入多数由 `local_conversation_fast_path` 处理，在调用云模型前已经返回，因此单纯更换或升级云模型无法修复。

### 4.2 平台否定作用域错误

`淘宝不要，京东可以`、`不看淘宝，但天猫要`、`只看淘宝，不要天猫` 全部错误。受控重跑中：

```text
输入：淘宝不要，京东可以
实际：platformsInclude=[]
实际：platformsExclude=[taobao, jd]
回复：不看淘宝、京东平台的结果
```

系统把整句中出现的所有平台统一应用同一个否定极性，没有分句作用域。

### 4.3 数值与相对操作错误

- `预算加200`：已有上限 500 时，实际变为 200，而不是 700。
- `再便宜一点`：上限仍是 500，只把排序改为价格升序。
- `预算不是500，是800`：仍保留 500。
- `1,500元以内`：得到 500。
- `至少1000但不要超过500`：系统接受 `priceMin=1000, priceMax=500`，没有冲突提示。

### 4.4 系统声称成功但状态未变化

受控工作流显示云模型经常生成正确自然语言回复，却没有产生对应 `filterRemove` 或状态变更：

- `价格不限`：回复“已清除价格限制”，`priceMax` 仍为 500。
- `品牌不限`：回复表达已取消，`brand` 仍为 Nike。
- `颜色随便`：`color` 仍为 black。
- `别按价格排了`：`sortRule` 仍为 `price_asc`。

这是高风险可信度问题：用户看到的是成功确认，后端实际仍按旧条件搜索。

## 5. 受控多轮工作流

每条工作流先通过云端建立明确状态，再发送目标指令并检查最终 `effectiveFilter`：

| 工作流 | 结果 | 最终状态 |
|---|---|---|
| 500 元上限 -> `价格不限` | 失败 | 仍为 500 |
| Nike -> `品牌不限` | 失败 | 仍为 Nike |
| 黑色 -> `颜色随便` | 失败 | 仍为 black |
| 京东 -> `平台无所谓` | 通过 | 平台限制清空 |
| 仅有货 -> `不要求有货` | 失败 | 仍为 true |
| 仅包邮 -> `不用包邮` | 失败 | 仍为 true |
| 旗舰店 -> `旗舰店不是必须` | 失败 | 仍为 flagship |
| 低价排序 -> `别按价格排了` | 失败 | 仍为 price_asc |
| 500 -> 300 -> `撤销刚才筛选` | 通过 | 恢复到 500 |
| 500 -> `预算加200` | 失败 | 变为 200 |
| 500 -> `再便宜一点` | 失败 | 仍为 500 |
| 42 码 -> `换大一码` | 失败 | 仍为 42 |
| 500 -> `不是500，是800` | 失败 | 仍为 500 |
| 鞋 -> `换手机` | 失败 | 仍为 shoe |

## 6. P1：高频理解缺口

### 错别字与俗称

已通过：`京冬`、`添猫`、`淘保`、`得务`、`拼夕夕`、`抖荫`、`鲜鱼`、`奈克`。  
失败：`惊东`、`咸渔`、`手鸡`、`耳鸡`、`跑斜`、`耐克谢`、全拼 `wo xiang mai nai ke xie`。

### 商品识别与类目

- `AirPods Pro 二代哪里便宜` 不触发搜索，类目为 general。
- `RTX 4060 游戏本` 不触发搜索，类目为 general。
- `鞋不看了，换手机` 仍保持 shoe。
- `电脑和手机都想看` 无法表达多类目。

### 尺码

5 条基础尺码用例全部失败，包括 `42码`、`42.5码`、`EU42`、中文尺码和范围；受控 `换大一码` 也失败。

### 取消、回滚与候选操作

- 平台取消、价格撤销和第三候选排除可用。
- 价格、品牌、颜色、库存、包邮、店铺、排序取消大多不可用。
- `前两个比一下` 能识别为比较。
- `第二个怎么样` 被识别为泛化购物建议，回复推荐了第一项，不是解释第二项。
- `换一批` 和 `改回上一个条件` 在模型 JSON 截断后退化失败。

## 7. 云端可用性问题

正式用例中出现 4 次 HTTP 502 和 3 次 HTTP 500：

- 502：`咸鱼上找个二手相机`、`只要全新的不要二手`、`500以下`、`找个降噪耳鸡`。
- 500：`预算不限`、`iPhone 15 哪里便宜`、`想买16GB内存的笔记本`。

长跑期间还观察到测试会话 seed 返回 502，健康检查随后恢复。测试框架没有将这些请求改成本地执行，也没有把原请求静默重试为成功。

## 8. 输入边界

- 缺失 message、空字符串、纯空白、非字符串均正确返回 400。
- 多行粘贴输入可正常处理。
- 十万字输入被云端接受并返回 201，耗时 48.6 秒；缺少明确长度上限，存在模型成本、资源占用和拒绝服务风险。

## 9. 已验证可用能力

- 标准耐克跑鞋搜索与正常中文预算。
- 中英文标准查询、繁体商品查询。
- 多个平台同时包含。
- 常见平台错别字中的 8/10。
- 标准库存、包邮和价格排序。
- 比较前两项、撤销最近一次价格修改、排除第三个候选。
- 纯 emoji、纯标点和提示词注入没有错误触发搜索。
- 非法负价格、文本价格、未知平台没有写入筛选状态。

## 10. 改进优先级

### P0

1. fast path 增加否定、取消、转折和作用域判定；有歧义时禁止跳过模型。
2. 对价格上下限、枚举、尺码和相对操作做状态层强校验，矛盾时追问而不是搜索。
3. 回复成功前核对实际 `effectiveFilter`；状态未变时不得声称“已清除/已更新”。
4. 修复云模型 JSON 截断解析，保留原响应诊断并进行受控结构化重试。
5. 调查 500/502 请求的云端日志、模型超时、数据库连接和实例资源。
6. 为文本请求设置长度和 token 上限。

### P1

1. 输入统一做 NFKC、零宽字符清理、繁简转换和模糊纠错。
2. 筛选 schema 支持多值 include/exclude、delta、软偏好、候选序号和类目切换。
3. 将取消、撤销、纠正、相对修改建模为一等操作，而不是普通字段覆盖。
4. 对候选指代保存明确的序号映射，避免“第二个”被解释成第一项建议。
