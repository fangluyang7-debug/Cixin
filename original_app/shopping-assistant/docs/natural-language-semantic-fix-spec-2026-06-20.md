## 0. 范围与排除项

本文只处理应用语义和状态问题，暂不处理以下云端响应异常：

- HTTP 500/502、Zeabur 实例可用性、网关与资源问题。
- 云模型返回截断或非法 JSON 导致的 `local_conversation_fallback`。
- 云模型网络、鉴权、超时和供应商稳定性。

因此，下列异常用例不作为本文语义根因的主要证据：

- HTTP 500/502：`I21`、`I22`、`I23`、`I24`、`I25`、`I26`、`I35`。
- 模型 JSON 异常：`F09`、`F16`、`F28`、`F41`、`F63`、`F75`、`F78`。

其余用例均来自移动端相同的云端链路。修改后的验收也必须继续使用该链路，不得用内部方法测试代替端到端结果。

## 1. 总体验收原则

所有问题都必须同时验证五层结果：

1. `intent` 是否正确。
2. `filterPatch`、`filterRemove` 或其他结构化操作是否完整。
3. 合并后的 `effectiveFilter` 是否符合用户语义。
4. 实际候选集合、排序或会话状态是否发生正确变化。
5. `assistantMessage` 是否与实际状态一致，不得声称未发生的操作已完成。

全局质量门槛：

- 本文 P0 用例端到端通过率必须达到 100%。
- 排除云端响应异常后，完整语义语料通过率至少达到 90%。
- 任意否定、取消或冲突语句不得静默反向执行；无法确定时必须追问。
- 所有状态修改都必须满足类型、范围和互斥约束。
- 修复不得破坏当前已通过的标准搜索、正常预算、平台别名、比较、撤销和候选排除能力。

## 2. 建议的内部语义表示

当前 `filterPatch + filterRemove + shouldResetPreviousFilters` 可以保留为持久化接口，但解析阶段需要增加一层内部语义操作，避免正则直接写最终状态。

建议结构：

```ts
type ShoppingOperation = {
  field: string;
  operator:
    | "set"
    | "include"
    | "exclude"
    | "remove"
    | "increment"
    | "decrement"
    | "restore_previous"
    | "reset_all";
  value?: unknown;
  polarity: "positive" | "negative";
  strength: "required" | "preferred";
  span: { start: number; end: number; text: string };
  confidence: number;
};
```

处理顺序应为：输入归一化 -> 分句 -> 实体和跨度识别 -> 极性/转折/相对操作识别 -> 语义操作 -> 状态校验 -> `filterPatch/filterRemove` 编译 -> 搜索 -> 基于最终状态生成回复。

## 3. 问题一：初始搜索路由过宽与信息不足

优先级：P0

### 3.1 问题表现

- 用户明确结束购买或否定搜索时，系统仍进入商品搜索。
- 用户只输入宽泛词语时，系统直接搜索而不是追问。
- 用户表达明确购买意愿但使用口语、俗称时，系统反而不搜索。

### 3.2 当前测试结果

| 用例 | 输入 | 期望 | 当前结果 |
|---|---|---|---|
| `I08` | `不买了` | 停止或普通对话 | 搜索综合商品，返回 117 个候选 |
| `I09` | `我不是要买鞋，只是问问怎么保养` | 建议/知识问答 | 启动鞋类搜索 |
| `I10` | `别给我推荐鞋` | 不搜索 | 启动鞋类搜索，返回 117 个候选 |
| `I11` | `买啥都行` | 追问类目和需求 | 直接搜索综合商品 |
| `I12` | `推荐一下` | 追问推荐什么 | 直接搜索综合商品 |
| `I13` | `鞋` | 追问场景/预算 | 直接搜索鞋 |
| `I17` | `I don't want shoes` | 不搜索 | 启动鞋类搜索 |
| `I04` | `想整个通勤用的头戴式耳机` | 搜索耳机 | 被当成非搜索对话 |
| `I07` | `AirPods Pro 二代哪里便宜` | 搜索耳机 | 不搜索，类目为 general |

### 3.3 问题出在哪里

- `sessions.service.ts:1762-1776` 的 `shouldStartProductSearch()` 使用宽泛关键词 OR，只要出现商品词、`买`、`推荐`、`预算` 等就返回 true。
- 该判断没有否定极性、购买状态、信息充分度和歧义门槛。
- `isAdviceFirstQuestion()` 只覆盖有限固定句式，口语表达无法稳定落入搜索或建议路径。
- 初始路由发生在云模型解析前，错误路由后不会再由模型纠正。

### 3.4 修改要求

1. 初始路由改为三态：`search`、`conversation`、`clarification`，不能只返回 boolean。
2. 加入明确的否定/退出意图：`不买了`、`不要推荐`、`只是问问`、`don't want` 等必须优先于商品关键词。
3. 搜索至少需要“购买/查找动作 + 可识别商品主体”，或“明确型号/商品 + 比价动作”。
4. 只有商品名但缺少动作时，根据上下文决定追问，不得默认搜索全商品池。
5. 口语动作扩展为可维护词典，例如 `想整个`、`来一个`、`康康`、`哪里便宜`。
6. 路由不确定时返回 `ask_clarification`，并给出针对性问题。

### 3.5 验收结果

- `I08-I13`、`I17` 不触发搜索，`conversationState.stateChangingTurn=false`。
- `I04`、`I07` 能识别商品主体并触发正确类目搜索。
- 新增不少于 30 条“商品词 + 否定词”变体，搜索误触发率为 0。
- 新增不少于 20 条信息不足输入，全部进入澄清，不创建有候选的搜索快照。
- 正常输入 `我想买一双耐克跑鞋` 仍触发搜索。

## 4. 问题二：输入归一化与纠错能力不足

优先级：P1

### 4.1 问题表现

- 当前只支持少量手工别名，同类错别字换一个字就失败。
- 全角字符、零宽字符、拼音、商品俗称和语音同音字不稳定。
- 品牌可能被识别，但商品类目仍丢失。

### 4.2 当前测试结果

已通过的平台别名包括 `京冬`、`添猫`、`淘保`、`得务`、`拼夕夕`、`抖荫`、`鲜鱼`。失败案例：

- `I02`：`奈克跑斜` 识别品牌 Nike，但类目为 general。
- `I19`：全拼 `wo xiang mai nai ke xie` 不搜索，不识别品牌和类目。
- `I20`：`耐克谢` 识别品牌，但类目为 general。
- `I33/F86`：带零宽字符的 `京​东` 无法识别。
- `I34`：`手鸡` 无法识别为手机。
- `I35`：`耳鸡` 需要在云端稳定后重测语义，当前词典没有对应别名。
- `F87` 全角 `ＪＤ` 可以由云模型处理，但本地归一化本身没有保证。

### 4.3 问题出在哪里

- `product-categories.ts:364-367` 只执行 trim、lowercase 和空格/下划线/连字符移除，没有 NFKC、零宽字符清理或繁简处理。
- `platform-normalization.ts:18-29` 与 `shopping-filter-heuristics.ts:109-147` 使用有限正则别名表。
- 品牌、类目、平台分别独立抽取，缺少统一纠错结果和置信度。
- 直接做全局模糊匹配会误伤型号和普通词，当前也没有受控白名单机制。

### 4.4 修改要求

1. 新增统一 `normalizeUserShoppingText()`：NFKC、零宽字符清理、大小写、全角数字/字母和常见标点归一化。
2. 繁简转换应在可控词典层完成，保留原始文本用于回复和审计。
3. 为平台、类目和高频品牌建立共享别名注册表，别名必须有 canonical value、来源和置信度。
4. 错别字纠正仅对购物领域白名单做编辑距离/拼音相似匹配，并设置最小长度与唯一候选门槛。
5. 低置信度纠错必须追问，例如“你指的是手机吗？”，不得静默改写。
6. 解析结果记录 `normalizedText`、命中的原文跨度和纠错来源。

### 4.5 验收结果

- `I02`、`I19`、`I20`、`I33`、`I34` 能得到正确搜索意图和类目。
- 零宽字符、全角字符和普通空格变形前后，结构化语义完全一致。
- 每个核心类目和平台至少覆盖 10 个错别字/同音/拼音变体。
- 对非购物文本运行纠错误改率低于 1%，任何非唯一候选进入澄清。
- 原始用户文本仍原样持久化，归一化文本只用于解析。

## 5. 问题三：否定、取消和极性被反向理解

优先级：P0

### 5.1 问题表现

系统识别到了库存、包邮、旗舰店、价格、颜色等实体，却忽略实体周围的否定词，最终应用与用户相反的条件。

### 5.2 当前测试结果

- `F46`：`不要500以上的` 得到 `priceMin=500`。
- `F53/W05`：`不要求有货` 后 `stockOnly` 仍为 true。
- `F54`：`不要有货的` 得到 `stockOnly=true`。
- `F56/W06`：`不用包邮` 后 `freeShippingOnly` 仍为 true。
- `F58/W07`：`不要旗舰店` 或 `旗舰店不是必须` 后仍为 `shopType=flagship`。
- `F61`：`不要最便宜的` 得到 `sortRule=price_asc`。
- `F26/F27`：`除了黑色`、`非黑色` 被当成只看黑色。

### 5.3 问题出在哪里

- `shopping-filter-heuristics.ts:72-105` 的库存、包邮、店铺和排序规则只检查关键词存在，不检查极性。
- 品牌和颜色虽调用 `isExclusionNear()`，但否定词集合有限，不能处理 `除了`、`非`、`不是必须`、后置否定等语法。
- `standard-conversation-intent-adapter.service.ts:45-46` 在模型前执行 deterministic fast path。
- 一旦本地规则抽出字段，`parseDeterministicTurn()` 会以固定置信度 0.78 直接返回，模型没有纠错机会。
- `turns.service.ts:1314-1317` 还会把本地 patch 覆盖到模型 patch 上，正确模型结果也可能被错误本地结果覆盖。

### 5.4 修改要求

1. 每个抽取值必须同时返回跨度、极性和操作符，不能只返回字段值。
2. 建立统一否定词和取消词集合，并支持前置、后置、`除了`、`非`、`不是必须`、`不要求`。
3. fast path 只允许单分句、单实体、无否定、无转折、无相对词的高精度表达。
4. 含否定、转折、两个以上值或相对操作的句子必须进入完整语义解析。
5. 本地规则与模型冲突时，不允许无条件用 local patch 覆盖；应进入校验或澄清。
6. `confidence` 必须来自实际证据，不能对所有 fast path 固定为 0.78。

### 5.5 验收结果

- 上述 `F46`、`F53`、`F54`、`F56`、`F58`、`F61`、`W05-W07` 全部通过。
- 为每个 boolean/枚举筛选字段增加正向、否定、取消、软偏好四组测试。
- 添加变形测试：在正向语句前加入 `不/不要/不用/不要求` 后，操作极性必须可预测地变化。
- 任何含否定词的输入不得走旧 deterministic fast path，除非规则明确产出负向操作并通过校验。

## 6. 问题四：平台否定作用域错误

优先级：P0

### 6.1 问题表现

一句话中同时出现允许和排除平台时，系统把所有平台统一当成排除项。

### 6.2 当前测试结果

- `F11/W15`：`淘宝不要，京东可以` 得到 `exclude=[taobao,jd]`，`include=[]`。
- `F12`：`不看淘宝，但天猫要` 同时排除淘宝和天猫。
- `F13`：`只看淘宝，不要天猫` 同时排除淘宝和天猫。
- `F14`：`除了淘宝都看` 没有正确得到淘宝排除。
- `F15`：`只看非闲鱼` 没有正确表达闲鱼排除。

### 6.3 问题出在哪里

- `platform-normalization.ts:101-108` 先抽取整句所有平台，再用一次 `isPlatformExclusionMessage(message)` 决定所有平台的极性。
- 没有按分句或平台实体跨度寻找最近的操作词。
- `platformsExclude` 使用累加语义，但新的 include 只消除相同平台；错误排除会持续污染后续会话。

### 6.4 修改要求

1. 先按逗号、顿号、转折词和连接词切分语义子句。
2. 对每个平台实体独立绑定最近的 `include/exclude` 操作。
3. 支持 `除了 X`、`X 之外`、`非 X`、`只看 X 不看 Y`。
4. 同一平台在同一轮同时出现 include/exclude 时，按最后明确指令或要求澄清，不得静默双写。
5. 输出 operations 后再统一编译 `platformsInclude/platformsExclude`。

### 6.5 验收结果

- `F11-F15`、`W15` 全部通过。
- 至少新增 30 条双平台/三平台混合极性用例。
- 最终状态必须满足 include 与 exclude 交集为空。
- 回复必须逐项复述：“排除淘宝，保留京东”，并与 `effectiveFilter` 一致。

## 7. 问题五：价格范围、纠正和相对修改不完整

优先级：P0

### 7.1 问题表现

- 区间只解析一端。
- 千分位、模糊价格和纠正表达错误。
- “增加/降低”被当成新的绝对值。
- 系统允许上下限互相矛盾。

### 7.2 当前测试结果

- `F39/F40`：`300到500`、`300-500` 无法稳定得到完整上下限。
- `F43`：`1,500元以内` 得到 500。
- `F47/W13`：`预算不是500，是800` 最终仍为 500。
- `F48`：口语纠正无法取最后有效值。
- `F77/W10`：已有 500 上限时，`预算加200` 变为 200，而不是 700。
- `F76/W11`：`再便宜一点` 只改变排序，价格上限仍为 500。
- `S03`：接受 `priceMin=1000, priceMax=500`，返回空结果而不是提示冲突。
- 正常 `五百以内`、`三百以上`、`至少500但不超过1000` 已通过，必须保留。

### 7.3 问题出在哪里

- `shopping-filter-heuristics.ts:26-69` 分别抽取 max/min，只取首个匹配，没有统一价格表达式 AST。
- 正则不完整支持千分位、小数、区间连接符、`左右`、`上下`、`k` 和相对变化。
- 纠正词 `不是/不对/改成/应该是` 没有“后项覆盖前项”的优先级。
- `FilterStateService.normalizeState()` 在 `filter-state.service.ts:197-207` 只把价格转成字符串。
- `applyField()` 在 `filter-state.service.ts:345-353` 不验证数值、正负、上下限关系。

### 7.4 修改要求

1. 建立统一 `PriceConstraint`：`min`、`max`、`target`、`tolerance`、`delta`、`currency`。
2. 支持中文数字、阿拉伯数字、千分位、小数、k、范围连接符和模糊表达。
3. 相对操作必须基于当前有效状态计算；没有基准时追问。
4. 纠正语句按转折后的最后明确值覆盖，不保留被否定值。
5. 合并后强制验证数值有限、非负且 `min <= max`。
6. 冲突不得进入搜索；返回 `ask_clarification` 并明确指出冲突条件。

### 7.5 验收结果

- `F39-F48` 中排除云响应异常后的语义用例、`F76/F77`、`W10/W11/W13`、`S03` 全部通过。
- `预算500，加200` 最终为 700；`降低100` 最终为 400。
- `300-500` 最终 `min=300,max=500`。
- 矛盾范围不创建候选快照，不返回“没有商品”，而是要求修正。
- 价格解析加入至少 50 条表格驱动测试和边界性质测试。

## 18. 问题十六：文本长度和资源边界缺失

- `B06` 返回 400 或 413，稳定错误码为 `TEXT_SESSION_MESSAGE_TOO_LONG`。
- 边界值 `max-1/max/max+1` 均有测试。
- 超限请求不产生 session、消息、模型费用或候选快照。

## 19. 问题十七：共享移动端账户导致上下文污染

优先级：P0

### 19.1 问题表现

不同设备和不同真实用户使用同一云端身份，用户记忆可能互相影响。云端审计中，大量未声明鞋码的会话自动带入 `size=42`。

### 19.2 当前测试结果

- 多个鞋类初始会话的 `effectiveFilter` 自动包含 size 42。
- 该值来自移动端固定账户的历史偏好，而不是当前输入。
- 使用同一固定账户会让测试和真实用户共享上下文，降低结果可解释性。

### 19.3 问题出在哪里

- `apps/mobile-flutter/lib/core/api/api_client.dart:37-38` 硬编码统一邮箱和密码。
- `_loginOrRegisterDeviceUser()` 让所有安装实例登录相同账户。
- `buildInitialTextFilter()` 将用户记忆 filter 放在文本解析之前合并，当前轮没有明确覆盖时会继承。

### 19.4 修改要求

1. 每个真实用户或设备必须拥有独立身份，不得共享生产凭据。
2. 测试使用独立测试账户并支持清理测试会话/记忆。
3. 继承记忆时在响应中标注来源；当前轮明确条件始终优先。
4. 对高影响偏好可首次复述确认，例如“沿用你之前的 42 码”。

### 19.5 验收结果

- 两台新设备获得不同 userId，历史与偏好互不影响。
- 新用户输入普通跑鞋时不自动继承其他用户的 42 码。
- 用户自己的已确认偏好仍可跨会话继承，并显示来源。
- 云端审计账户与生产用户身份完全隔离。
