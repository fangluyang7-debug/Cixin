# 技术方案与实现策略（V0）

## 1. 文档目的

本文档用于把前面的产品定义、模块边界、数据对象和 MVP 优先级，进一步转化为可执行的技术方案框架。

这里重点回答的是：

- 当前项目在技术上应该如何组织
- 各模块更适合采用什么实现方式
- 哪些能力适合优先用规则实现，哪些适合交给模型
- 数据源、会话、降级和扩展能力应该如何预留
- 哪些技术决策已经确认，哪一项仍未定

## 2. 当前已确认的技术约束

截至当前版本，已经确认的技术约束如下：

1. 安卓客户端采用 `Flutter`
2. 规划 `抖音小程序` 作为后续第二前端入口，当前仅保留入口位，不展开前端技术路线
3. 若后续接入抖音小程序，两条前端入口共用一套后端业务逻辑
4. 后端采用 `Node.js`
5. Node.js 后端框架采用 `NestJS`
6. 首版数据库方案采用 `SQLite + Prisma`
7. 当前 MVP 不引入 `Redis` 等独立缓存组件，但从架构层预留统一缓存接口
8. 图片存储正式路线采用 `国内对象存储`，代码层保持 provider-neutral，当前默认腾讯云 COS
9. 商品数据源主路线采用 `ProductPool 商品池 + 多平台数据注入`；聚合搜索 API 只作为后续可选适配路线
10. 首版品类只做 `鞋`
11. 每个品类都要有自己封闭的 `字段结构 + Prompt 模板 + 规则映射`
12. 首版目标是打通 `拍照 -> 多平台结果 -> 自然语言多轮收敛`
13. 评委体验形态采用 `形态 B`，即评委自行安装并在线体验应用
14. 当前 MVP 评委入口采用 `APK + Web 展示页 + 安装说明`
15. 抖音小程序不进入当前 MVP 交付范围，但需作为后续扩展路线预留
16. 后端托管平台采用 `Zeabur`
17. Web 展示页采用 `Zeabur 静态服务`，APK 下载文件采用 `国内对象存储`，当前默认腾讯云 COS
18. 当前 MVP 图片上传采用 `服务端中转`
19. `CandidateItem` 采用混合结构：核心字段强结构，扩展字段保留 JSON
20. 当前 MVP 采用 `NestJS` 进程内轻缓存 + `SQLite` 快照 + 固定 fallback 结果承接缓存与恢复
21. 历史价格、配送时效属于完整产品能力，当前不进入首版验收；用户长期记忆基础模块已纳入后端能力，但长期画像写入必须经用户确认

## 3. 当前未完成核心技术项

当前真正未完成的核心技术项是：

1. 真实平台商品数据持续注入
2. 多平台采集器稳定化
3. 商品图片质量与 embedding 覆盖率提升
4. 云端轻量用户图主体定位能力

聚合搜索 API 不再是当前主路线。后续如果重新接入聚合搜索 API，应作为商品源适配器之一，而不是替代商品池主链路。

## 4. 技术方案设计原则

无论你后面怎么选具体框架，当前实现策略建议遵守以下原则：

### 4.1 主链路优先

所有技术设计都优先服务于首版闭环，不为完整产品的远期能力提前引入过重复杂度。

### 4.2 模型负责理解，规则负责控制

当前最合理的实现边界是：

- 模型负责商品理解、自然语言解析、建议文案生成
- 规则负责筛选、生效约束、排序控制和降级兜底

这样做的原因是：

- 可解释性更强
- 调试成本更低
- 多轮收敛更稳定
- 演示时更可控

### 4.3 外部依赖必须可替换

商品数据注入、模型供应方、embedding provider、历史价格来源等外部能力都不应直接写死在核心逻辑里，而应通过适配层接入。

### 4.4 品类扩展必须结构化

鞋类首版不能写成一次性逻辑，必须从一开始就按“品类模板”思路组织：

- 品类字段结构
- 识别 Prompt
- 筛选解析 Prompt
- 候选映射规则
- 排序维度规则

### 4.5 降级能力必须从首版开始预留

这个项目高度依赖外部模型和外部商品源，因此降级不是后补功能，而是首版演示可用性的组成部分。

## 5. 当前建议的总体技术架构基线

在不替你最终定框架的前提下，当前最适合作为实施基线的总体结构是：

`客户端`
-> `Node.js API 层`
-> `应用编排层`
-> `领域模块层`
-> `外部适配层`
-> `存储/轻缓存/降级层`

### 5.1 客户端

负责：

- 拍照或上传图片
- 展示候选列表与商品详情
- 接收自然语言追加筛选
- 保持当前会话内的前台状态连续

当前前端路线分成“首版已定”和“后续规划”两层：

- 首版安卓 App 采用 `Flutter`
- 抖音小程序作为后续第二入口，但其前端技术路线暂未最终拍板，且当前不纳入 MVP 交付

因此后续实现需要把“客户端界面实现”与“后端业务逻辑”明确拆开：首版先完成 Flutter 路线，但后端能力从一开始就不应与某个单一前端深度耦合。

### 5.2 Node.js API 层

负责：

- 对外暴露统一接口
- 接收图片上传、筛选请求、详情请求
- 组织响应结构

它的定位是“接口入口层”，不承载复杂业务判断。

### 5.3 应用编排层

负责：

- 串联商品理解、搜索、候选池更新、智能建议和决策辅助
- 维护一次查询从开始到结束的完整调用顺序
- 管理多轮会话内的业务推进

这个层是当前技术方案的核心。

### 5.4 领域模块层

负责：

- 承载 `03` 中已经定义的模块边界
- 让每个模块只处理自己的核心职责
- 避免控制器里堆满跨模块逻辑

### 5.5 外部适配层

负责：

- 模型调用适配
- 聚合搜索 API 接入
- 托管对象存储接入
- 历史价格来源接入
- 未来配送时效数据接入

### 5.6 存储 / 轻缓存 / 降级层

负责：

- 查询会话存储
- 候选结果缓存
- 外部结果快照
- 降级数据读取
- 演示兜底恢复

当前这一层已经确认采用“主存储 + 轻缓存”结构：

- `SQLite + Prisma` 负责主存储与可恢复快照
- `NestJS` 进程内轻缓存负责短期热点数据和结果复用
- 固定 mock / fallback 数据负责演示兜底

同时，当前线上托管基线已经确认采用 `Zeabur`，因此后续部署方案应默认按：

- `NestJS` 服务运行在 Zeabur Node.js Service
- `SQLite` 绑定 Zeabur Volume，建议路径为 `/data/prod.db`
- `国内对象存储` 承载图片对象存储，当前默认腾讯云 COS

## 6. Node.js 后端实现策略

你已经确认后端使用 `Node.js + NestJS`。因此这里不再比较后端框架，而是直接按 NestJS 风格约束后端的组织方式。

### 6.1 API 接口层

负责：

- 处理图片上传请求
- 处理自然语言追问请求
- 处理候选列表、详情、会话恢复等请求

建议策略：

- API 层只做输入校验、鉴权预留、响应组织
- 不在这里写识别、搜索、排序、候选池更新逻辑

在 NestJS 中，这一层通常对应 `Controller`。

### 6.2 应用服务层

负责：

- 组织一次完整查询流程
- 组织多轮收敛流程
- 协调会话状态、候选池和外部能力调用

建议策略：

- 用应用服务承接“一个请求触发多个模块协作”的逻辑
- 每条主链路至少有一个清晰的应用服务入口

在 NestJS 中，这一层通常对应面向用例编排的 `Service`。

### 6.3 领域模块层

建议按前面已经收束的模块边界组织：

- 商品理解
- 跨平台检索与聚合
- 结果标准化与候选池
- 结果筛选与收敛
- 智能建议
- 决策辅助
- 商品详情
- 会话与状态保持
- 缓存、降级与恢复

在 NestJS 中，这一层建议以业务模块拆分，每个模块有自己的 provider、规则和适配器入口。

### 6.4 外部适配层

建议单独抽出两类适配器：

- `模型适配器`
- `商品源适配器`

原因是这两类依赖最容易变动，也是最容易在比赛中出故障的地方。

在 NestJS 中，外部适配层适合通过独立 provider 封装，并通过模块注入到应用服务层。

当前图片相关能力通过 provider-neutral 存储适配器接入，而不是把某个对象存储 SDK 直接散落在业务模块中。当前默认 provider 为腾讯云 COS，后续若切换 OSS/COS/其他对象存储，只替换 adapter 与环境变量。

### 6.5 数据访问与缓存访问层

你已经确认首版采用 `SQLite + Prisma`，但当前 MVP 又要控制成本，因此后端访问策略建议拆成两类：

- `Prisma 数据访问`
- `轻缓存访问抽象`

建议策略：

- Prisma 负责正式数据写入、会话持久化、可恢复快照
- 进程内轻缓存负责短期热点结果、搜索结果复用、模型结果复用和降级兜底加速
- 业务模块不应直接依赖某个具体缓存产品，而应通过统一缓存接口访问

在 NestJS 中，这一层适合通过独立 provider 或 service 封装，例如：

- 数据库访问 provider
- 缓存访问 provider

## 7. 模块级实现策略

这一节不再重讲职责，而是讲“每类模块更适合怎么实现”。

### 7.1 用户输入与会话启动模块

建议实现策略：

- 以一次图片输入作为一次查询会话起点
- 上传成功后立即返回会话标识
- 后续自然语言追问、候选刷新、详情查看全部挂到这个会话上

原因：

- 多轮连续交互必须有稳定会话锚点

### 7.2 商品理解模块

建议实现策略：

- 使用多模态模型完成鞋类商品理解
- 输出必须严格对齐鞋类品类模板
- 允许用户在识别后修正关键属性

实现重点：

- 模型输出必须结构化
- 不能把“自由文本识别结果”直接丢给搜索模块

### 7.3 跨平台商品数据与检索模块

建议实现策略：

- 通过商品池进行候选召回
- 真实平台数据由爬虫、授权接口、半自动整理或人工样本写入商品池
- 每次导入都保留原始平台 payload 与导入批次审计
- 不同平台数据先统一标准化为商品池结构，不要在采集器里硬编码最终排序

实现重点：

- 数据阶段优先解决“可写入、可去重、可追踪、可生成 embedding”
- 搜索阶段优先解决“从商品池召回”
- 排序和解释留给后面的模块

### 7.4 结果标准化与候选池模块

建议实现策略：

- 定义统一的候选商品内部结构
- 所有平台结果必须先归一化，再进入后续流程
- 当前会话下只维护一个主候选池

实现重点：

- 候选池是多轮筛选的基础
- 不允许每一轮追问都绕开候选池重新拼装一套结果

### 7.5 结果筛选与收敛模块

建议实现策略：

- 使用 LLM 把自然语言请求解析成结构化筛选条件
- 用规则引擎在候选池上执行条件生效
- 当现有候选池不足时，再决定是否补充检索

实现重点：

- 先在候选池内收敛，再考虑重新搜索
- 不要把每轮自然语言输入都当成“重开一次新搜索”

### 7.6 智能建议模块

建议实现策略：

- 建议卡片可以先采用规则驱动
- 主动推荐结论可以由规则结果 + 文案生成组合完成
- 首版不需要复杂推荐系统

实现重点：

- 建议必须建立在候选事实和当前筛选条件之上
- 建议输出不能脱离当前候选池乱给结论

### 7.7 决策辅助模块

建议实现策略：

- 汇总价格、平台、货源、建议结论等信息
- 生成列表可比较标签和详情解释信息
- 首版可先用轻量规则整合，不必上复杂打分体系

实现重点：

- 它负责把“已有信息组织成人可理解判断”
- 不要把它写成另一个搜索模块

### 7.8 商品详情模块

建议实现策略：

- 详情应基于已有候选商品对象展开
- 详情数据以“补充解释和补充比较”为主
- 不在详情页重新做一套独立数据链路

### 7.9 会话与状态保持模块

建议实现策略：

- 会话状态必须中心化维护
- 保留当前商品画像、筛选条件、候选池和浏览状态
- 支持用户在同一会话中连续多轮追问

实现重点：

- 会话状态比“纯接口无状态”更重要
- 否则首版的连续交互会失真

### 7.10 缓存、降级与恢复模块

建议实现策略：

- 搜索结果保留短期缓存
- 识别结果保留短期缓存
- 为外部模型和外部商品源各准备一条降级兜底路径

实现重点：

- 这个模块在比赛环境中优先级很高
- 首版就应该具备可演示的兜底方案

## 8. AI 能力实现策略

### 8.1 AI 在当前项目中的角色划分

当前更合理的划分是：

- `VLM`：负责图片理解
- `LLM`：负责自然语言筛选解析、建议文案生成、部分解释生成
- `规则`：负责筛选生效、约束控制、候选排序、降级处理

### 8.2 Prompt 组织策略

基于你前面确认的“品类封闭结构”要求，Prompt 不应散落在代码里，而应按品类组织。

建议至少拆成三类 Prompt：

1. 商品理解 Prompt
2. 自然语言筛选解析 Prompt
3. 建议与解释生成 Prompt

每一类 Prompt 都应挂到“鞋类模板”下。

### 8.3 品类模板策略

鞋类首版建议把以下内容绑定在一起维护：

- 鞋类字段结构
- 鞋类识别 Prompt
- 鞋类筛选解析 Prompt
- 鞋类候选映射规则
- 鞋类筛选约束映射规则

后续扩品类时，直接按同样结构新增模板，而不是复制主流程代码。

### 8.4 模型输出控制策略

建议：

- 模型输出必须尽量结构化
- 关键对象进入业务流程前必须经过格式校验
- 不接受“看起来像 JSON 但不稳定”的自由输出直接进入主链路

## 9. 商品数据源接入策略

### 9.1 ProductPool 商品池主路线

当前路线已经收束为 `ProductPool 商品池`。后端搜索链路不直接依赖淘宝、天猫、京东、得物、拼多多、抖音电商等平台的实时页面，也不把某个聚合搜索 API 作为主前提。

建议结构：

- 商品导入契约
- 平台原始 payload 保存
- 商品标准化映射
- 商品图上传与主体预处理
- 商品图 embedding 生成
- ANN 索引写入
- 候选召回与融合排序

当前候选结果标准化策略也已经进一步确认：

- `CandidateItem` 中当前主链路一定会用到的字段采用强结构
- 供应商扩展字段与当前不进入主链路的原始返回结果保留在 JSON 中

### 9.2 平台数据注入策略

后续即使更换某个平台的数据采集方式，也应尽量只改：

- 采集器或授权 API 适配器
- 原始平台字段到商品池导入契约的映射

不改：

- 会话逻辑
- 商品理解逻辑
- 收敛逻辑
- 决策辅助逻辑

### 9.2A 聚合搜索 API 预留策略

聚合搜索 API 可作为后续商品源补充，但不再是当前主路线。

若后续接入，必须以 provider 形式写入商品池或标准候选结构，不得绕过：

- 商品池导入契约
- 候选标准化
- embedding/ANN 检索链路
- 会话状态与候选快照

### 9.3 历史价格与配送时效数据策略

由于历史价格和配送时效目前不进首版验收，当前策略建议是：

- 在对象和模块边界里预留位置
- 不强行在首版绑定真实稳定来源
- 等你后面决定是否推进这两块，再单独接入供应源

## 10. 数据存储与状态管理策略

### 10.0 当前主存储基线

首版主存储已经确认采用：

- `SQLite` 作为数据库引擎
- `Prisma` 作为数据访问与迁移管理层

当前这样选择的意义是：

- 首版复杂度可控
- 关系型结构足够支撑会话、候选池、筛选条件和降级快照
- 后续如果迁移到更正式的关系型数据库，Prisma 层可以保留较多结构连续性

### 10.1 当前必须持久化的内容

即使首版不做完整用户系统，以下内容也建议有明确存储归属：

- 查询会话
- 原始输入引用
- 商品画像
- 当前筛选条件
- 候选池快照
- 降级数据

同时，图片本体不建议进入 SQLite，而应进入 `国内对象存储`；数据库只保存图片元数据与引用关系。当前默认 provider 为腾讯云 COS。

### 10.2 当前建议缓存的内容

- 识别结果缓存
- 商品搜索结果缓存
- 候选池缓存
- 降级用 mock 结果

这些内容当前建议优先通过进程内轻缓存承接；若后续真实调用成本或用户量上升，再替换为独立缓存组件。

### 10.3 当前建议延后复杂化的内容

- 完整用户长期画像
- 历史价格长期仓库
- 复杂推荐特征存储

### 10.3A 图片存储策略

当前已确认：

- 图片正式存储路线采用 `国内对象存储（当前默认腾讯云 COS）`
- SQLite + Prisma 只保存图片元数据、引用关系和所属会话信息
- 图片压缩主位置放在 `Flutter` 客户端
- 首版采用“双轨图片”思路：压缩识别图先进入主链路，原图按需补传
- 国内对象存储采用多个 bucket 分开存储不同类型图片
- 本地文件系统最多作为开发期临时调试或演示兜底，不作为正式主存储

当前建议图片链路如下：

`Flutter 本地轻压缩`
-> `上传压缩识别图`
-> `NestJS 接收并中转`
-> `国内对象存储（当前默认腾讯云 COS）`
-> `数据库记录压缩图 object key / URL / 会话关系 / 状态信息`
-> `必要时按需补传原图`

这样做的主要原因是：

1. 评委 demo 更稳定
2. App 打包后更自然
3. 后续迁移、分享、扩展和权限控制更容易
4. 能同时优化上传耗时与模型解析耗时
5. 不需要在首版把所有图片都按原图规格立即传输

当前建议的双轨角色分工如下：

- `压缩识别图`：优先用于上传、商品理解、搜索主链路和缓存复用
- `原图`：按需补传，用于后续调试、人工复核、重跑识别或后续扩展能力
- `演示样例图`：独立于真实业务上传数据，用于 demo、mock 和稳定兜底

当前建议的 bucket 分工如下：

- `compressed-recognition bucket`：承载压缩识别图
- `original-source bucket`：承载按需补传原图
- `demo-assets bucket`：承载演示样例图

### 10.3B 用户实时图像处理与商品离线图像处理边界

当前必须严格区分两类图像处理：

1. 用户实时图像处理
2. 商品池离线图像处理

用户实时图像处理必须全部在云端完成：

`上传图片`
-> `COS 存储`
-> `云端轻量主体定位`
-> `返回 normalized bbox 给前端展示`
-> `用户可调整 bbox`
-> `云端按当前有效 bbox 裁剪 / 标准化`
-> `豆包图片 embedding`
-> `ANN 检索`

本地 GPU 不得成为这条链路的必需环节，因为开发机无法保证长期在线。

商品池离线图像处理可以使用本地 GPU：

`采集 / 样本商品图`
-> `本地 GPU 主体提取`
-> `标准化裁剪`
-> `本地或在线 embedding`
-> `写入商品池 embedding`
-> `云端搜索时直接读取`

这样划分的原因是：

- 云端 CPU/内存有限，只适合轻量即时能力
- 用户实时体验要求随时可用
- 商品入库和 embedding 重建可以离线慢处理
- 前端不应感知本地 GPU 是否存在
- 后续可单独替换商品图 embedding provider，不影响用户实时链路

这里的重点不是“极限压缩”，而是：

- 在客户端做保守的轻压缩
- 优先降低过大的手机原图尺寸
- 保留鞋类识别需要的轮廓、颜色和主要纹理特征

当前对象存储层还可继续细化的，不是“是否分桶”，而是：

- 各 bucket 的最终命名
- 是否还要在 bucket 内继续按日期、会话或环境加 prefix

### 10.4 当前 MVP 缓存策略

当前已确认：

- 当前 MVP 不引入 Redis
- 当前缓存以 `NestJS` 进程内轻缓存为主
- 跨重启恢复优先依赖 `SQLite` 快照与固定 fallback 结果
- 正式业务状态仍然只由数据库承担

它在当前项目中的角色主要有 4 个：

1. 识别结果复用  
   同一图片或同一可识别输入不必重复走完整识别链路。

2. 搜索结果复用  
   相同商品画像和相近筛选条件下，优先复用已有搜索结果。

3. 会话内中间结果加速  
   多轮追问时，候选池与中间结果可通过缓存快速恢复。

4. 降级兜底  
   外部模型或外部商品源失败时，优先读取缓存结果做兜底。

当前更建议视为“值得保留能力语义、但不要求独立缓存跨重启保存”的缓存包括：

- `fallback:*`
- 固定 demo 样例结果
- 最近热点 `recognition:*`
- 最近热点 `search:*`

而以下内容即使进入未来缓存层，也不应被当成正式持久化对象：

- 查询会话正式状态
- 当前生效筛选条件正式版本
- 当前候选池正式恢复版本

### 10.5 缓存接口预留策略

既然你已经确认后面仍可能重新引入独立缓存组件，那么当前实现不应把缓存能力写成“某个产品的临时用法”，而应从第一版开始定义统一接口。

建议至少预留以下缓存能力接口：

- `get(key)`
- `set(key, value, ttl)`
- `delete(key)`
- `exists(key)`
- `getOrSet(key, ttl, loader)`

建议至少按以下逻辑域划分缓存命名空间：

- `recognition:*`
- `search:*`
- `session:*`
- `fallback:*`

建议从第一版开始约束：

- 业务模块不直接拼底层缓存命令
- 缓存 key 生成逻辑统一收口
- TTL 由业务场景决定，不在控制器层硬编码
- 缓存未命中时，主链路必须能回退到数据库或外部能力

### 10.6 当前对缓存层的收束结论

当前已经确认的不是“完全不要缓存”，而是：

- 当前 MVP 先不用独立缓存基础设施
- 先以进程内轻缓存 + SQLite 快照 + 固定 fallback 数据支撑主链路
- 后续若真实调用成本、并发或稳定性要求上升，再把同一套缓存接口替换到 Redis 或等价产品

## 11. 部署与评委体验策略

### 11.1 当前已确认的体验形态

当前已经确认：

- 不存在线下现场演示机会
- 评委需要自行安装并体验应用
- 应用安装与上手路径应尽量短

这意味着当前项目的正式演示形态不是“答辩现场主讲操作”，而是：

`评委拿到下载入口`
-> `安装安卓应用`
-> `连接线上后端`
-> `自行完成主链路体验`

### 11.2 这一形态对整体架构的直接影响

既然评委要自行体验，当前架构必须满足：

- 后端必须公网可访问
- 对象存储必须为线上可访问形态
- App 内的 API 地址不能依赖本地局域网或开发机
- 应用安装包必须易获取，且安装说明尽量短
- 主链路不能依赖你在现场手动切换环境

### 11.3 当前已确认的评委入口方案

当前已经确认采用：

`APK 安装包`
`+`
`Web 展示页`
`+`
`简短安装说明`

其中各部分承担的角色如下：

- `APK` 负责最终安装与运行
- `Web 展示页` 负责承载项目介绍、下载入口、体验说明和必要截图
- `安装说明` 负责降低评委从点击到成功安装的摩擦

当前这条 MVP 路径的目标不是“应用商店式分发”，而是：

`让评委在最短文字说明下拿到 App`
-> `完成安装`
-> `进入线上可用主链路`

### 11.4 这一方案的直接影响

既然当前 MVP 采用的是 `APK + Web 展示页 + 安装说明`，那么：

- Web 页必须足够轻，不能把评委导向复杂注册或多层跳转
- 下载按钮必须明显，且 APK 文件版本应清晰可辨
- 安装说明必须极短，优先解决“如何安装 APK”这一件事
- Web 页应补充最少量的产品说明、截图和体验提示，避免评委下载前不知道装的是什么
- 主下载入口和备用入口最好同时存在，避免单链接失效

同时，后续如果补入抖音小程序路线，也应复用同一套后端逻辑，不能变成一套完全不同的产品叙事。

当前入口托管基线已经进一步确认：

- `Web 展示页` 采用 `Zeabur 静态服务`
- `APK 文件` 采用 `国内对象存储（当前默认腾讯云 COS）`

这样做的意义是：

- 展示页继续和当前 Zeabur 部署体系保持一致
- APK 文件下载直接使用 腾讯云 COS 作为文件分发落点
- 入口页和文件存储职责分离，不把大文件下载耦合到静态站本身

### 11.5 当前入口层仍可继续细化的事项

入口形态和入口托管基线都已经确定。当前这一层剩下的只是可继续细化的问题：

- 二者是否共用同一域名或同一平台
- 是否为评委再补一条视频演示或图文流程作为辅助入口

## 12. 演示与降级策略

这个项目的外部依赖高，所以演示策略应提前写进技术方案。

### 12.1 模型降级

如果图片理解失败：

- 返回预设识别结果
- 或切换到可控的样例图与样例输出

### 12.2 搜索降级

如果聚合 API 失败：

- 返回本地 mock 候选结果
- 或返回最近一次缓存结果

### 12.3 会话恢复

如果中途请求失败：

- 尽量保留当前会话
- 允许用户回到最近一次有效候选结果继续操作

### 12.4 演示约束

为了降低现场风险，建议：

- 准备一组固定演示图片
- 准备对应的可控 mock 结果
- 准备至少一条完整主链路的离线或半离线兜底方案

## 13. 客户端实现策略基线

当前客户端是双入口：

- 安卓 App：`Flutter`
- 抖音小程序：前端技术路线待定

因此这里的实现策略重点不只是“做一个 Flutter 客户端”，还包括：

- 保证两条入口复用同一套后端逻辑
- 保证两条入口在核心链路上语义一致
- 把前端特有差异限制在交互层与容器能力层

前端入口至少应承担：

- 图片采集与上传
- 候选列表展示
- 自然语言筛选输入
- 当前会话状态展示
- 商品详情承载

前端入口至少应维护：

- 当前会话标识
- 当前商品画像展示状态
- 当前候选列表
- 当前筛选条件
- 当前自然语言输入历史
- 当前详情查看状态
