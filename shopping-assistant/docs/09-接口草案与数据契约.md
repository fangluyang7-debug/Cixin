# 接口草案与数据契约（V0）

## 1. 文档目的

本文档用于在产品边界、模块边界、核心数据对象、技术方案和存储方案已经明确的前提下，进一步定义当前系统的接口草案与数据契约。

这里重点回答的是：

- 当前后端应暴露哪些核心接口
- 每个接口服务于哪条业务链路
- 请求与响应至少应承载哪些数据
- 哪些接口属于 MVP 必须落地
- 哪些接口只预留结构，不进入当前 MVP 验收

本文档讨论的是“接口草案”，不是最终 OpenAPI 文件，也不是最终 DTO 字段命名锁定版。

## 2. 当前范围与边界

与本文件直接相关的当前边界如下：

1. 首版核心链路是 `拍照 -> 多平台结果 -> 自然语言多轮收敛`
2. 首版只做 `鞋`
3. 当前 MVP 正式交付路径是 `APK + Web 展示页 + 安装说明`
4. 后端采用 `Node.js + NestJS`
5. 当前主存储为 `SQLite + Prisma`
6. 当前 MVP 不引入独立缓存组件，缓存以进程内轻缓存和数据库快照复用为主
7. 图片正式存储采用 `国内对象存储`，代码层保持 provider-neutral，当前默认腾讯云 COS
8. 历史价格、用户记忆、配送时效不进入当前 MVP 验收
9. 抖音小程序是后续扩展路线，不进入当前 MVP 交付范围
10. 图片压缩主位置放在 `Flutter` 客户端
11. 首版采用“双轨图片”：压缩识别图先走主链路，原图按需补传
12. 当前 MVP 图片上传采用 `服务端中转`
13. `CandidateItem` 采用混合结构：核心字段强结构，扩展字段保留 JSON

因此，当前接口设计应优先服务：

- Android Flutter 客户端
- 会话式查询过程
- 可恢复的多轮状态更新
- 候选池统一读取
- 后续前端扩展时对同一后端逻辑的复用

## 3. 接口设计原则

### 3.1 会话优先

当前接口应围绕 `QuerySession` 组织，而不是围绕一次次无状态搜索临时拼接。

原因是：

- 当前主链路本身就是多轮连续交互
- `04` 和 `08` 都已经把会话作为核心锚点
- 后续无论是 Flutter 端还是小程序端，都更适合复用同一套会话语义

### 3.2 先定义资源关系，再定最终传输细节

当前接口草案优先定义：

- 有哪些资源
- 资源之间如何关联
- 资源如何被读取和更新

而不在这一版强行锁死：

- 图片上传的最终 multipart 组织方式与表单细节
- 最终 DTO 的每个字段名是否完全固定
- 所有扩展字段是否都暴露到前端接口

### 3.3 当前草案优先采用“异步会话”思路

由于当前链路中包含：

- 图片理解
- 外部商品检索
- 候选标准化

这些步骤都存在明显耗时，因此当前草案更适合按：

`创建会话`
-> `后端处理`
-> `客户端读取当前状态`

来组织。

这样做更贴合：

- 当前数据库快照设计
- 降级状态表达
- 多前端复用

### 3.4 当前 MVP 与后续能力分开

接口层也必须维持相同边界：

- 当前 MVP 只定义其真正需要落地的主接口
- 后续能力可以预留接口位，但不能在这一版默认为首版必做

### 3.5 统一返回结构优先于前端特化

当前接口不应为某一个前端入口单独变形出一套独立语义。

更合理的方式是：

- 统一核心业务返回结构
- 前端自己决定显示层组织

### 3.6 `CandidateItem` 契约采用混合结构

当前已经确认：

- 候选商品的核心展示、筛选、排序字段保持强结构
- 标准化扩展属性保留在 `normalizedAttributes`
- 供应商原始返回结果保留在 `rawPayload`

接口层默认不要求把 `rawPayload` 暴露为当前 MVP 前端的主读取对象。

## 4. 资源模型总览

当前建议把接口资源分成 7 类：

1. 图片资源 `ImageAsset`
2. 查询会话 `QuerySession`
3. 商品画像快照 `ProductProfileSnapshot`
4. 会话轮次 `SessionTurn`
5. 筛选快照 `FilterSnapshot`
6. 候选池与候选商品 `CandidateSnapshot / CandidateItem`
7. 智能建议与详情结果 `Suggestion / CandidateDetail`

在当前草案中，它们的主关系链建议理解为：

`ImageAsset`
-> `QuerySession`
-> `ProductProfileSnapshot`
-> `SessionTurn`
-> `FilterSnapshot`
-> `CandidateSnapshot`
-> `CandidateItem`

## 5. 通用数据契约约定

### 5.1 通用响应包裹结构

当前建议所有业务接口统一采用如下外层结构：

```json
{
  "success": true,
  "requestId": "req_xxx",
  "data": {},
  "error": null
}
```

失败时：

```json
{
  "success": false,
  "requestId": "req_xxx",
  "data": null,
  "error": {
    "code": "SESSION_NOT_FOUND",
    "message": "Session does not exist.",
    "details": {}
  }
}
```

### 5.2 标识字段约定

当前建议：

- 所有业务主键均采用不透明字符串
- 不让前端依赖自增 ID 语义

例如：

- `assetId`
- `sessionId`
- `turnId`
- `candidateSnapshotId`
- `candidateItemId`

### 5.3 时间字段约定

当前建议所有时间字段统一使用：

- `ISO 8601`
- `UTC`

例如：

- `2026-05-23T10:30:00Z`

### 5.4 金额字段约定

当前草案建议金额统一封装为对象，而不是裸数字：

```json
{
  "amount": "499.00",
  "currency": "CNY"
}
```

这样当前不会被过早绑定到：

- 前端小数展示方式
- 后端内部精度表示方式

### 5.5 状态字段约定

当前建议会话状态至少区分：

- `created`
- `processing_profile`
- `searching`
- `ready`
- `degraded_ready`
- `failed`

候选商品货源状态至少预留：

- `in_stock`
- `out_of_stock`
- `unknown`

### 5.6 空值与缺失字段约定

当前建议：

- “字段存在但当前无值”使用 `null`
- “当前版本完全不返回该能力”则直接不出现该字段

例如：

- 当前 MVP 不做真实历史价格时，不必在所有列表结果里强塞空的 `priceHistory`

### 7.1 `POST /api/v1/assets/images`

**作用**

创建图片资源，返回后续可供会话使用的 `assetId`。

**优先级**

P0

**说明**

当前已确认首版图片上传采用“客户端压缩后，由后端接收并中转到国内对象存储”的方式，当前具体供应商为腾讯云 COS。

Day 1 P0 阶段先实现图片资源语义登记与存储引用生成；Day 3 起同一接口兼容 `multipart/form-data`，字段名为 `file`，服务端中转到当前 storage adapter。本地 mock 生成对象引用，腾讯云 COS 环境变量齐全时执行真实上传。

同时，当前已经确认两点：

- 图片压缩主位置在 `Flutter` 客户端
- 首版采用双轨图片，压缩识别图优先进入主链路，原图按需补传
- 当前 MVP 上传链路采用服务端中转

因此该接口当前主要表达：

- 图片资源接入语义
- 双轨图片语义
- 服务端中转后生成的资源引用语义

但当前建议资源语义至少能表达：

- 当前上传的是压缩识别图还是原图
- 当前图片是否作为主链路识别图使用
- 是否属于同一拍摄组

**请求体草案**

JSON 调用方式至少应得到：

```json
{
  "assetGroupId": "asset_group_xxx",
  "variantType": "compressed_recognition",
  "isPrimaryRecognitionAsset": true,
  "sourceType": "camera",
  "clientContext": {
    "platform": "android_app"
  }
}
```

multipart 调用方式：

- `file`：压缩识别图、原图或 demo 图文件
- `variantType`
- `isPrimaryRecognitionAsset`
- `sourceType`
- `assetGroupId`

**响应体草案**

```json
{
  "success": true,
  "requestId": "req_xxx",
  "data": {
    "assetId": "asset_xxx",
    "assetGroupId": "asset_group_xxx",
    "variantType": "compressed_recognition",
    "isPrimaryRecognitionAsset": true,
    "uploadStatus": "uploaded",
    "imageRef": {
      "assetId": "asset_xxx",
      "provider": "tencent_cos",
      "bucketGroup": "compressed-recognition",
      "bucketName": "shopping-assistant-dev-compressed-recognition",
      "region": "ap-guangzhou",
      "objectKey": "2026/05/24/pending-session/asset_group_xxx/asset_xxx.jpg",
      "publicUrl": "https://..."
    }
  },
  "error": null
}
```

`uploadStatus` 当前允许：

- `registered`：JSON 语义登记，尚未携带真实文件
- `uploaded`：multipart 文件已由服务端中转给当前 storage adapter

## 11. 接口链路与调用顺序

### 11.1 当前 MVP 主链路

建议当前前端按下面顺序使用接口：

1. 上传图片，拿到 `assetId`
2. 创建查询会话，拿到 `sessionId`
3. 读取会话状态，直到会话进入 `ready` 或 `degraded_ready`
4. 读取当前候选池
5. 用户发起自然语言追问
6. 再次读取会话状态和候选池

### 11.2 P1 增强链路

当主链路稳定后，可补：

1. 读取建议卡片
2. 查看候选详情

### 11.3 后续扩展链路

后续如果接入：

- 商品画像修正
- 历史价格
- 用户长期记忆
- 配送时效

则在当前会话语义之上继续追加接口，不改变当前主链路骨架。

## 13. 当前接口定稿口径

当前接口层补充定稿如下：

1. 双轨图片使用同一上传接口，通过 `variantType` 区分压缩识别图与原图
2. 详情接口按 `candidateItemId` 读取
3. MVP 候选池列表不做真正分页，默认返回当前快照完整列表
4. 金额字段保持 `{ amount, currency }` 对象结构，`amount` 使用字符串
5. 建议卡片使用固定 `actionType + params` 结构，不扩展为通用 DSL

## 14. 当前文档结论

到这一层为止，当前接口层已经可以形成一套足以支持首版实现设计的骨架：

- 当前接口按 `会话式查询` 组织
- 当前 MVP 只要求落地 `资产接入 / 会话创建 / 会话读取 / 多轮追问 / 候选读取`
- P1 接口补充建议和详情
- P2 接口继续保持为扩展位

## 15. 后续已实现补充：用户画像长期记忆接口

当前后端已新增正式账号体系与跨会话用户画像模块。该能力不改变匿名 demo 主链路；未登录用户仍可创建会话，但不会写入长期画像。

### 15.1 账号接口

- `POST /api/v1/auth/register`：邮箱密码注册，返回 `Bearer` JWT。
- `POST /api/v1/auth/login`：邮箱密码登录，返回 `Bearer` JWT。
- `GET /api/v1/users/me`：读取当前登录用户信息。

### 15.2 用户画像接口

- `GET /api/v1/users/me/profile`：读取完整长期画像块。
- `GET /api/v1/users/me/profile/context?category=shoe`：读取当前任务可用画像上下文。
- `POST /api/v1/users/me/profile/blocks`：用户主动新增画像块。
- `PATCH /api/v1/users/me/profile/blocks/{blockId}`：用户主动编辑画像块。
- `DELETE /api/v1/users/me/profile/blocks/{blockId}`：删除画像块。

### 15.3 待确认记忆接口

- `GET /api/v1/users/me/memory-proposals`：读取系统从对话中提取出的待确认记忆。
- `POST /api/v1/users/me/memory-proposals/{proposalId}/confirm`：确认写入长期画像。
- `POST /api/v1/users/me/memory-proposals/{proposalId}/reject`：拒绝写入长期画像。

### 15.4 会话链路变化

`POST /api/v1/sessions` 支持可选 `Authorization: Bearer <token>`。带 JWT 创建的会话会绑定 `userId`，并把用户画像中的相关偏好带入会话上下文与初始筛选，例如排斥平台。

`POST /api/v1/sessions/{sessionId}/turns` 会在登录态下生成 `memoryProposals`，但不会直接修改长期画像。长期画像的唯一生效路径是用户确认 proposal 或用户主动编辑 profile block。
