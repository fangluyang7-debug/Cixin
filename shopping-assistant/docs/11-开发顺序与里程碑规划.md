# 开发顺序与里程碑规划（V1）

## 1. 文档目的

本文档用于把当前已经确认的 MVP 边界、技术方案、接口草案和目录规划，进一步收束为一套**满负荷冲刺版**开发顺序与里程碑安排。

这里重点回答的是：

- 在不砍骨架的前提下，四天内如何冲完整 MVP
- 当前完整 MVP 应包含哪些交付内容
- 四天窗口里每一天必须交出什么结果
- 哪些工作必须并行推进，不能串行慢做
- 哪些事项虽然高风险，但在本计划中仍按“必须完成”处理

本文档讨论的是“极限冲刺型开发排期”，不是常规节奏下的理性排期。

## 2. 当前计划口径

本版文档采用以下口径：

1. **不砍当前 MVP 骨架**
2. **P0 必做模块全部落地**
3. **P1 模块全部进入四天范围，不再按“可简化可不做”处理**
4. **P2 仍然只保留结构，不进入当前四天实现范围**

也就是说，当前四天计划中的“完整 MVP”定义为：

- 完成 `拍照 -> 多平台结果 -> 自然语言多轮收敛` 主链路
- 同时完成：
  - 智能建议
  - 决策辅助
  - 商品详情
  - 缓存、降级与恢复
- 同时完成：
  - APK 打包
  - Web 评委入口页
  - 线上部署

## 3. 当前四天窗口定义

本计划按以下四天推进：

- `2026-05-25`
- `2026-05-26`
- `2026-05-27`
- `2026-05-28`

目标是：

**到 `2026-05-28` 结束时，交出一个可安装、可上线、可演示、具备完整 MVP 骨架的版本。**

## 4. 当前完整 MVP 的交付范围

本计划中的“完整 MVP”当前明确包括：

### 4.1 核心链路

1. 用户拍照或上传鞋图
2. 系统完成鞋类商品理解
3. 系统返回多平台候选结果
4. 用户查看价格与货源结果
5. 用户通过自然语言追加筛选
6. 系统在同一会话中更新候选结果
7. 用户可连续多轮追问

### 4.2 同步进入四天范围的增强能力

1. 智能建议模块
2. 决策辅助模块
3. 商品详情模块
4. 缓存、降级与恢复模块

### 4.3 同步交付能力

1. 安卓 APK
2. Web 展示页
3. 安装说明
4. Zeabur 线上后端
5. 腾讯云 COS 图片存储链路

### 4.4 当前仍不进入四天实现范围

即使本版不砍 MVP 骨架，以下内容仍不进入当前四天开发：

- 抖音小程序
- 历史价格真实链路
- 配送时效真实链路
- 非鞋类品类扩展
- 应用商店分发

这些不是“被砍掉的 MVP”，而是当前就不属于 MVP 的 P2 或后续规划。

说明：用户长期记忆基础模块已进入后端能力范围，但长期画像写入必须经用户确认，不作为无确认自动记忆处理。

## 5. 当前四天冲刺的执行前提

本计划默认以下前提成立：

1. **按高强度连续开发推进**
2. **任务按并行方式分发，不按单线程慢做**
3. **真实商品数据注入即使未完全稳定，也必须尽快形成可用商品池和可替换采集适配**
4. **mock / fallback 不是降配方案，而是完整 MVP 的稳定性组成部分**
5. **UI 视觉质量要跟进，但不能阻塞主链路**

本计划不讨论作息合理性，也不按保守团队节奏估算。

## 6. 当前建议的并行工作流

四天内不能按“先后端、再前端、最后部署”的单线思路做。  
必须拆成至少 4 条并行工作流：

### 6.1 后端主链路流

负责：

- NestJS 服务骨架
- 会话
- 图片上传
- 商品理解
- 聚合搜索
- 候选池
- 多轮追问
- 详情 / 建议 / 决策辅助
- fallback

### 6.2 Flutter 客户端流

负责：

- 拍照/上传
- 候选列表
- 自然语言输入
- 详情页
- 建议卡片
- APK 打包

### 6.3 交付与部署流

负责：

- Zeabur 部署
- SQLite 线上持久化
- 腾讯云 COS 对象存储
- 评委入口页
- 安装说明

### 6.4 数据与样例流

负责：

- 鞋类样例图
- mock 结果
- fallback payload
- 提示词调试样例
- 演示路径固定样例

如果是多人推进，应至少让这 4 条流并行。  
如果是单人推进，也必须按“时段切块并行”思路推进，而不是死盯一条线。

## 7. 当前完整 MVP 的模块落地要求

本计划中，以下模块全部视为四天内要落地：

### 7.1 P0 模块

1. 用户输入与会话启动模块
2. 商品理解模块
3. 跨平台检索与聚合模块
4. 结果标准化与候选池模块
5. 结果筛选与收敛模块
6. 会话与状态保持模块

### 7.2 P1 模块

1. 智能建议模块
2. 决策辅助模块
3. 商品详情模块
4. 缓存、降级与恢复模块

这里的关键变化是：

**P1 这次不再按“可选增强项”处理，而按“完整 MVP 应同步交付的模块”处理。**

## 8. 开发顺序总原则

即使不砍骨架，开发顺序仍然必须服从以下原则：

1. **先打通数据链，再做表现层增强**
2. **先做“能跑”，再做“更好看”**
3. **先做列表与多轮，再做详情和建议**
4. **部署与 APK 不能放到最后一天才第一次碰**
5. **fallback 必须在第 3 天前具备，不允许最后一天才想起来补**

## 9. 四天详细里程碑

## 9.1 Day 1：`2026-05-25`

**目标**

把完整 MVP 的工程骨架和最短可运行主链路搭起来。

**当天必须完成**

后端：

- 建好 `services/api-server/`
- 配好 `NestJS + Prisma + SQLite`
- 建核心持久化对象：
  - `QuerySession`
  - `ImageAsset`

  - `SessionTurn`

  - `CandidateItem`

  - `turns`

  - `details`
  - `fallback`

  - `POST /api/v1/assets/images`

  - `GET /api/v1/sessions/{sessionId}/candidates`

  - 拍照/上传页

部署与资源：

- 配好 对象存储 bucket 基础环境变量
- 准备鞋类样例图和 mock 数据

**Day 1 验收标准**

- 仓库结构完整落地
- 后端能启动
- Flutter 工程能启动
- 会话能创建

### 10.1 A 层：主链路核心

- 上传与拍照
- 会话
- 商品理解
- 搜索
- 候选池
- 多轮追问
- 状态保持

### 10.2 B 层：完整 MVP 同步交付项

- 智能建议
- 决策辅助
- 商品详情
- fallback 与恢复
- Web 评委入口页
- APK
- 线上部署

### 10.3 C 层：当前仍不进入四天实现

- 小程序
- 历史价格真实链路
- 配送时效真实链路

用户长期记忆基础模块已进入后端能力范围；本节不再把它视为完全未纳入事项。

## 11. 当前四天计划中的关键卡点

### 11.1 商品池与真实数据注入

这是当前后端真实链路的核心数据来源。

在本计划里，它不能继续停留在“后面再看”。
必须在开发开始后尽快进入两种状态之一：

1. 已导入一批图片可访问、可生成 embedding、可检索的商品池数据
2. 已形成一个不阻塞主链路的样本 / fallback product pool

聚合搜索 API 不再是主路线，只作为后续可选商品源适配。

### 11.2 多轮状态一致性

四天里最容易表面能演示、实则最容易坏掉的就是：

- 识别结果
- 当前筛选条件
- 候选池
- 建议卡片
- 详情信息

这几块不同步。

所以 Day 3 不能只看“能刷新”，还要看“刷新后上下文没断”。

### 11.3 交付与部署

如果 Day 3 才第一次碰：

- Zeabur
- 腾讯云 COS
- APK
- 评委入口页

那风险会非常高。

因此本计划默认这些工作最迟 Day 2 晚上就要开始联调。

### 11.4 UI 完整度

你既然明确要求“不砍骨架”，那 UI 上至少不能只停留在裸调试页。

这不意味着 Day 1 就先抠动画，而是：

- Day 2 开始就要同步建设结构化界面
- Day 4 再统一收视觉和交互

## 12. 当前文档结论

到这一层为止，当前项目已经被收束成一套“**四天完整 MVP 冲刺计划**”。

当前最重要的结论是：

- 当前计划不再按保守降配写
- 四天内目标是交付完整 MVP，而不是最小残缺版
- P0 与 P1 模块全部进入本轮实现范围
- 真实平台商品数据注入、商品图片质量和 embedding 覆盖率仍然是最大不确定项
- mock / fallback 不是降级路线，而是完整 MVP 的稳定性组成部分
- Day 3 必须完成首轮线上完整闭环
- Day 4 必须完成补稳、补界面和最终交付
